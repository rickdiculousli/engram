# Technical decisions

The machinery calls, made without the owner (they read outcomes, not machinery), each with its why. The owner's own calls are under Decisions in the private `.engram/README.md`; this doc implements them. How search and the timeline work is in [search](search.md); summaries in [summaries](summaries.md).

## How work is measured

- **Scripts first, no model usage.** A change is measured by script before anything live: whether one call's output holds each key record, and how big it is. Why: full live runs burn the week's quota, and a coverage script predicts their results.
- **Live runs are small:** about 10 questions, with a stated question each run settles, their cost reported afterwards. A full run's noise is larger than most changes.
- **What counts:**
  - a single fact: in hand after one move, the `engram now` picture plus the top 5 of the question as one search, any record code calls the same, else the key's values in one record (`evalset.fact_in_hand`, [evaluation](evaluation.md#the-bar-100)). Each row of the picture is its own record for the key's values: read as one text, it holds a key's values on unrelated rows, a hollow pass. A `now` row counts for an entry on its chain only where its own line holds the key's values.
  - a frame question: every record it needs in one timeline call, counted per record as well as per question
  - size: estimated at four characters a token, against grep's measured tokens
- **The baseline is grep** (`engram eval --mode grep`), run in a clone of the real repo with its own instructions, hooks and skills, capture off.
- **Look at the record's real items before building on it.** List every kind of file with its sections per file, decide what one real-world thing is for each, and read real output rows by eye, not only counts: a count can't see one report showing up as many rows.
- **Check a bar by arithmetic before adopting it.** At a per-record find rate of 0.89, "all records, in all 3 runs" passes a 6-record question about 11% of the time.
- **A session-origin question never sees its own session:** `ENGRAM_EXCLUDE_SOURCES` hides the session's docs from search and timelines, and its said rows (`session:<id>:…`) everywhere.
- **The sealed held-out set is never opened while tuning.** Children (subagents, `claude -p`) run at a named effort, medium or below.
- **Expected refs follow the record when it moves.** Evals match refs as exact strings (`evalset.hit`), so when a record's files move, each old ref in a set is replaced by its new homes from the move's map: array elements only, no question text, kind or note changed, checked field by field against a copy.

## Said rows

What the owner said in a session becomes rows on its threads, drawn from the stitched session summaries at ingest (`sources/said.py`), so a timeline shows what was only said beside what was filed.
- **What:** symptom reports, other reports, decisions and the changes the owner stated (a summary's update whose evidence is in the owner's own words, `summarize.said_by`, credited to them), and from the chronology the entries the owner said and outside sources' words passed on, credited to that source. Claude's own analysis, advice and second thoughts stay out (a change Claude made to its own reading is the summary's, never a row on the owner's thread), and so do records filed during the session and open questions.
- **Placement:** an occurrence sits on its recurring thread's threads; anything else on the threads its top 10 hits vote for, keeping any within 60% of the top vote. Placing is a search per passage, so it runs in the hourly job and `engram ingest`, never while a question waits ([when the index is read](#when-the-index-is-read)).
- **Each row** is dated the day its turn was said (the summary keeps each turn's day, `days`), quoted, and points to the session line: `session:<id>:<line>@said-<section>-<n>`.
- **Only indexed sessions:** a session kept out of the index (eval work) stays out.
- **A summary made before days and speakers were kept** gets both from its session with no model call (`summarize.complete`), in its stitched summary and in the segments a later stitch is rebuilt from; a session cleaned up from the box is fetched from the mirror for it. While its session can't be read, its rows stay as they were: dated the day the turn's segment began, its updates all shown and credited as worked out with Claude.
- **Unplaced analyses:** an open question or discovery file none of whose sections is on a thread is placed by the threads its opening 80 words find as a search (`sources/place.py`, source `placed`). Only the record's own analyses are placed: placing every unplaced document finds no more records, for more tokens.
- **An entry with no thread** takes the threads of the other entries in its series, or on its thing's chain, most entries first (`events.inherited`); a pooled series gives none.

## When the index is read

- **A question reads the record again when it changed** (`ingest.refresh_if_stale`, in search and timeline): the domain's settings, the day, the commit and the size and time of each changed or new file under the record's folder make one hash (`ingest.state`), kept with the last read; one that can't be told never counts as read. Why not a timer: a fact filed a minute ago was missing from the next answer, and a timeline never looked at all. A pack's own sources sit outside git, so those are still read again after 15 minutes.
- **What's built by searching the record waits for the hourly job:** the threads of what was said in sessions and of documents on none take a search per passage, which made a search wait many seconds. The hourly job ends by reading every domain whole, so they're at most an hour behind the record.
- **One read of a domain at a time** (`<domain>.lock`): a question finding one under way waits a few seconds for it, reads only if the index is still behind, and past that answers from the index as it is. Why: two reads at once collided on the same rows, and several questions asked together each started their own.
- **A timeline keeps within Claude's window** (`timeline.fit`, [search](search.md#the-one-call-timeline)). Why fold rather than cut or print: past the window Claude Code hands over a preview and a file, so the advisor read none of it in order. The rows folded are day-to-day rows of the stories the search picked, which the owner's lens rule ranks last; what the caller named, a row inside the question's period, and any row another row or the theory points at never fold, and a fold that wouldn't print shorter isn't made.

## Stable document ids

Link ends must survive a moved file or a reworded heading.
- **One registry, no front matter** (`docreg.py`, `events/docs.jsonl`): appended to only, mapping each id to its path and each anchor to its heading; the latest line wins. Why not an `id:` in front matter: anchors need a registry anyway, text files can't hold front matter, an id line would change every page the owner reads, and the pre-commit looks at moves anyway. Ids are `doc-` and six characters from the short-name alphabet; anchors four. A path row may carry `thing` (from `[nodes]`), so a renamed thing file still resolves.
- **What gets one:** every indexed document gets an id; a heading gets an anchor the first time a link points at it, since an anchor on an unlinked heading protects nothing and would make every heading edit a pre-commit question. `engram docs sync` does both in one store commit; the hourly job runs it.
- **Resolving** at read time, never rewritten: `doc-…#anchor` through the anchor's heading now; an old `path#Heading` through every path and heading the registry has held; a merged document or section through its forward. The index's link table holds where each end stands now. `engram show` takes an id or an old end.
- **New links write ids** (`engram link`, capture's placement, the re-link job), with `from_hint`/`to_hint` holding the path and heading as they read.
- **The rename check** (`engram lint --staged`): a staged change that deletes or moves a document a link points at, or drops a linked heading, is refused unless the staged registry places it. A pure `git mv` and a one-to-one heading rename are recorded by the hook itself; each refusal prints the exact `engram moved <old>[#heading] <new>[#heading]` command.
- **`events/_nodes.jsonl`** (kind, milestone, `by` and threads of record sections that aren't entries) is kept by hand; `engram nodes prune` drops rows whose file is gone, and the append-only lint lets it lose whole rows and nothing else.
- **Index excludes in the record:** `[index] exclude` in the record's `engram.toml`, merged with the domain's configured excludes; `engram exclude <path>` adds one in one store commit.

## Mechanical errors

`engram fix [<event files>] --why <the error> [--drop-link <id>]... [--drop-run <commit>]` (`fix.py`) commits the listed event files as edited or deleted, drops the listed lines from links.jsonl, and pushes: one commit, `engram fix: <why>` with an `Engram-Fix: <why>` trailer. `--drop-run` undoes an evidence sweep whole, and takes several commits when a backlog landed over several runs: it drops every link of the sweep's author those commits filed that's still there, and its message carries git revert's line for each, so the weekly page treats each run as reverted and its line goes. The pre-commit's append-only check lets exactly those paths through (`ENGRAM_FIX`). It refuses, changing nothing, when a listed file is unchanged or wasn't an event, an edit changes the id or doesn't parse, another event file or links.jsonl has uncommitted changes, a link id isn't found, a link left behind points at a deleted event, or the run named filed no sweep link that's left. The advisor asks the owner before a fix; it is for what the machinery got wrong, never for something learned later.

## Theory revisions

`engram theory change` (`theorychange.py`) takes flags for one revision, or `--ops -` for a JSON list: add-node, add-loop, insert-step / remove-step, add-join / retire-join, status. `plan()` applies the whole list to a copy of the graph and refuses on the first problem: an unknown id, a join kind or strength the record's `[links.theory]` doesn't know, a retirement without `replaced_by` and `why`, a loop left with fewer than two steps, a closed loop that no longer closes, or an open chain that's no longer one path. New steps and joins are lines of links.jsonl; a retired link gets a status entry on `link/<id>`. `theory.load(asof=...)` drops what's dated later, so `engram theory --as-of` shows what was thought then.

A structural change starts `engram theory relink --change <id>` detached (`relink.py`): every entry and document is read whole, packed into calls of at most 90k characters, and code keeps a new link only if its record is in the batch, its target is part of the change, its rel is strengthens or weakens, and it isn't held already. Links are by=claude. A change runs once; the hourly job runs one still queued after 10 minutes or left running for 3 hours; one that errored waits for a hand rerun, since a retry spends money, and shows one line in `engram now` until it's rerun.

## The evidence sweep

`engram theory sweep` (`relink.sweep`, beside the re-check), the linking job, links the whole record's moments to its theory, which the re-check never does on its own: it reads only after a structural change, and the filer writes timeline links and agreed joins, never evidence.
- **The link kinds are the record's** (`relink.kinds`): with none named, strengthens and weakens (family `evidence`) on loops and Discoveries. A record may name its own in `[links.moment]` (family `moment`): each rel a table with its `label`, what it `means` (the words the read and the confirming call are given), the theory kinds it may point at (`to`, on the kind rather than the theory kind's table, since a loop's built-in kind has none; with no `to`, any the job reads against: every theory kind a kind names, or with none named, the loops and the record's own theory kinds), and `owner_words`, whether its passage must be the owner's own. The sample's are showed up (it was active), set off by (what triggered it, the words in which it speaks being it showing up), did differently, didn't fit and eased (his own words only). Why: a belief like "I'm unlikable" isn't a claim to weigh, so a moment says what happened, and "nobody likes me" said on a bad night can't count for it; and one lookup, with strengthens and weakens as its default, keeps one linking job.
- **What it reads:** the re-check's records (`records()`, the pack's `relink_skip` left out) without journal entries, in calls of at most 30k characters at medium effort, each with every target (a loop's path drawn) whole, in the pack's `sweep` words, and the kinds listed (`{rels}`). A note is dated its session's day. Never read: the guide's suggestions (`by: claude-suggestion`, an entry or a theory page: an idea isn't something that happened), and what `[links.moment]` skips by who said it (`skip_by`) or by kind (`skip_kinds`). Why: a large batch at low effort misses most of what bears on the theory. For strengthens and weakens, questions are phrased either/or, so for and against mean nothing for them, and nodes, states and treatments are left out because the theory block never prints their evidence.
- **The guards are the re-check's** (`_check`): the record is in the batch, the target is one the kinds point at, the rel is one of the record's kinds and may point at that theory kind, and the pair isn't linked already, in any form a target is named (its id, its file, a section, its document id): by any rel for strengthens and weakens, which exclude each other (`one_way`), by that rel for the record's own kinds. Why: in one moment the critic can show up and be answered, and the belief show up while what happened doesn't fit it; a single kind would hide the news. In a record that has lines of the owner's (a note, an entry of his that quotes him), and for a kind that needs his own words, the passage must be in one of them (`notes.spoken`: the lines that name him as their speaker; the question a reply answers is the guide's), wherever the record keeps notes or a kind needs his words. Why: a note and a reply hold the guide's words beside his, and "that sounds lighter" or the question he answers "yeah" to is the guide's, not a moment of his. The read also cites the record's own words that bear on it (`passage`), found word for word in the record. A document's passage that restates one entry is that entry's evidence: one entry's own words (a table line), or a dated index row (a date, a dash, a headline) whose row links to the entry or whose headline is the one entry's title, that day's when several are. The link moves to the entry (`_entry_of`), and "already linked" drops it as a repeat; a passage no one entry fits stays the document's. Why: pages restate their entries' headlines, so one observation would count under a target several times. The re-check applies the same guard.
- **A second call confirms each link** (the pack's `sweep_confirm`): it sees the record whole, its passage, the target and the rel with what that kind means, never the read's reasoning, and only a yes is filed. Why: a weekly machine read with no owner in the loop needs an independent check before anything lands, and the passage, since a long document's evidence can be one passage of it. Asking it twice adds nothing: the same prompt gets the same verdict.
- **Filing is the re-check's transaction** (`_file`): by=claude, author `engram-sweep`, in the kinds' family, titled with the kind's label, the passage as the link's note, Claude's placement, never the owner's claim, in one commit: for strengthens and weakens one whose `Refinement:` line is the weekly page's, for the record's own kinds the hourly job's (`moments`). `--dry-run` files nothing; `--out` writes every proposed, dropped, confirmed and rejected link.
- **A run never starts a call that could take it past $10** (`SWEEP_CAP`: it leaves room for its dearest call so far), and the next run picks up where it stopped. Its progress (`sweep/<domain>.json` in the data folder; a dry run keeps its own, `.dry.json`) holds each record read and at which text, and the links still to confirm or file: a run confirms what waits first, then reads only records new or changed since, against every target, and the records read already against a target added since (a suggestion or a belief the filer adds, a Discovery), against it alone; a target that goes needs nothing read again. Why: a record's whole backlog can cost more than one run may spend, and reading it again against every target for each one added would cost the whole read each time the filer adds one.
- **Links engram placed stay open to the theory work** (`recheck`): only `engram-sweep`'s and `engram-relink`'s, by=claude, never the owner's. They're read again by the confirming call, in the same words, against the target as it stands now: when a structural change revises their loop (`run`, before it reads), when a weekly run finds their loop or Discovery's text changed since its last read (the progress keeps each target's version, the hash of what the calls see of it), and on request, `engram theory recheck <target>`. A no drops the link through `engram fix` (`--drop-link`), one commit per run whose `Refinement:` line is the weekly page's, and remembers it against that version of its target (`sweep/<domain>.dropped.json`); a guard of both the sweep and the re-check refuses it until the target changes. Re-reading against an unchanged target gives the same answer, so a sharpened claim is what prunes a stretch.
- **Hourly, where the kinds say so** (`[links.moment] hourly`; `relink.hourly`): the hourly job runs it after filing, whether or not the repo's weekly pass is paused, with its progress as its mark: a run with nothing new or waiting makes no call, a target added costs one read of the record against it alone, and one that stops at its $10 cap waits a day (`HOURLY_WAIT`, `sweep/<domain>.stopped`). Why: an inner-work record's weekly pass stays paused, a session's moments are worth linking while it's fresh, and with nobody watching an hourly job a backlog must cost at most one cap a day. One record's runs take turns (`relink.lock`, `sweep/<domain>.lock`), the hourly job's, a look-back's and the weekly pass's. Why: two at once read the same links as unfiled and file them twice.
- **A look-back** asks for one thing (`engram theory sweep <thing>`, `items`): every record is read again against it alone, apart from the progress, under the same guards and cap. Why: a look-back reviews one insight's whole history.
- **History:** a theory thing's moments show on its row of a history (`timeline._moments`): a count per kind's label, then each moment with its kind, date, headline and record, oldest first within its kind; for and against only where the kinds are strengthens and weakens.
- **Weekly:** `engram refine run` runs it for each domain whose pack has `sweep` words, before the passes, once a week by its own mark. Its ledger rows (`job: sweep`) count toward the week's spend, so the passes' money left counts them, but the passes' "already ran" check and status ignore them; `engram health` tells its outcome, a $10 stop or a failure included (an unknown cost counts its whole cap). It's skipped when the repo is paused, and a dry run runs nothing.
- **A replay** (`--replay FILE`) lands an approved set with no model calls: the recorded proposals answer each read and the approved (passage, target, rel) answer the confirming call, and every guard runs against the record as it stands. Why: a set read against a scratch copy lands on the live record exactly as approved.
- **Undo** is `engram fix --drop-run <commit>` ([mechanical errors](#mechanical-errors)).
- **Left out:** corrections and disagreements (a machine read can't tell a correction from separate occurrences by the record's own fields; that belongs to the filer, at filing time).

## The filer

The hourly job (`engram capture run`: `hourly.py` runs it and the session start's health check, `capture.py` files, `setup.py` installs and repairs) indexes changed sessions, keeps the summaries current for the set-up repos and any domain whose config says `summaries = true`, files each session that grew and has been idle an hour (or its repo's pause, [notes](#notes)), summarizes the long records of each area it files for ([summaries](summaries.md#record-summaries)), and repairs the install.
- **Routing:** a session belongs to the repo it was started in (its project folder name, else its first working folder), a subfolder or a worktree of it.
- **A message that also loads a skill is still the owner's** (`sessions._said`): the harness writes it as a command line and, under it, one line of its own, the typed text first; only that text is the turn, and a rewind that takes the message back takes it too.
- **A rewound message was never said** (`sessions.parse`, so for every reader of a session): a rewind keeps the old messages in the file, so where two typed messages follow the same one, the one off the branch the session ended on is dropped with all that followed it, Claude's replies included. Why: otherwise a retracted answer files as a fact, and the answer that replaced it attaches to a question from the dropped branch. A fact filed before its message was rewound stays until the owner says so.
- **It reads the session whole** (in a repo with notes, a session at a time: [notes](#notes)), cleaned like the summaries, from the message it last filed up to. A session still going is skipped. Most sessions file nothing, and are still marked. The model sees what the session already filed, read from the store by `source` (`said in session <short id> ` or `agreed in session <short id> `, without its placement links and renewals), so a refiled session doesn't file it twice; the mark is the only state kept per session. Why: the record is the one copy of what was filed.
- **Code drops a fact** unless it's from the owner's own words: its quote in one of their messages past that point, word for word, and every number in their words or the question they answered. That question must be in Claude's turn just before their message (`capture.turn_before`): all Claude's text since their previous message, past a skill's turn, a summary or another speaker, and the current turn's text before what they sent while Claude worked. A plan or decision (`capture.AGREED`), where the record keeps that kind, is theirs to adopt from Claude: its numbers may also be ones Claude gave in its last five turns before their words (`capture.RECENT`). Why: "that's the plan" comes some turns after the plan was laid out, and the decision was otherwise lost with its amounts. Why not a quote of the plan: the filer doesn't reliably cite what was agreed to, and a plan's amounts sit in tables no quote copies. So for a plan or decision, what the reply says they were answering is kept only when Claude asked it just before, and otherwise left out of the entry, never the reason to drop it. Any other kind keeps to their words and the question, since an "ok" after Claude's analysis doesn't make its figures theirs. A number counts only whole (`dates.numbers`): "35" isn't in "135B", while "7 out of 10" passes on "7/10". It counts by its value: "2,000" is his "2000", and "2" his "two" or "twice" (`capture.spelled`; never "one", mostly a pronoun, nor the first word of a larger number). One glued to letters before it (B12, CO2, a model number) is part of a name, and counts when that whole name is in the question he answered or anywhere in his own messages of the session. Why: the model's headline writes his number its own way, and he names a thing once and says "it" after; dropping the fact over either lost what he said. Claude's words elsewhere in the session never supply one, and a when or a how-often written that way (mid-2024, week-6, Q3, q6h, x2), or any year, is no name: said of one thing earlier, it would date or dose another.
- **What the model sees of the record:** every entry dated within 31 days either side of each message's day, where each tracked thing stands (the `now` chains), and search hits; any fact a listed entry states, in any words, is a repeat.
- **The repeat check:** after the code checks, each candidate's own title and body search the index; its top 8 hits across entries, documents, occurrence pages and where-things-stand, whole up to 1,500 characters, plus every entry dated the same day, go to one low-effort call per session (`verify`), which names the record that already states each repeat. Code drops it only if that ref was shown under it. A new occurrence of a known thing is always filed: for an occurrence kind (the pack's `occurrence_kinds`), the named record's date must fall within 2 days of the candidate's (4 when either is approximate). One exception, where the model's verdict stands: a candidate he gave no date for, named as a repeat of a form this same session saved (`capture.forms`: a document the session wrote or edited that carries no written date, YYYY-MM or YYYY-MM-DD, anywhere in its name or text). An intake form the advisor filled in from his answers was otherwise filed again as an entry per answer; a dated candidate, or a saved page that carries a date anywhere (a visit brief, even in a section that doesn't), is still judged by its dates. Why: the owner's raw words miss records worded differently.
- **His date words:** code reads the phrases in a fact's quote that say when (`capture.relative_days`), from the day he said it. As a day: today (N hours or minutes ago too), yesterday, N days, weeks, months or years ago (calendar months and years), since <weekday>, this or last week, `approx` when estimated (`periods.of` widens it when read). As two ends, `range_from` to `range_to` with `date` the first and `approx`: last or this <season> and <season> <year> (`periods._when`'s season branches, the day said as today), early, mid or late <month or year> (days 1–10, 11–20, 21 to the end; January–April, May–August, September–December), "N or M <units> ago", and "a couple of <units> ago" (1 to 4 units back). A span is one phrase, and no day inside it is read again. Half a unit counts ("half a year ago", "1.5 years ago", "a year and a half ago"), a count never starts inside another number, and "the day before yesterday" is two days. One plain count of 24 hours or more ago counts back to the nearest day, always as an estimate; with another number or a bound before it in its clause ("24 to 48", "less than 24"), or "or so" after, it's left as it was read before. Why: each of these filed as a wrong day, stated firmly. Early, mid or late May without its year needs a word like "in" before it ("late may" is mostly the verb). The phrase goes into `as_said` word for word. A day written out is one of the quote's phrases, with no words to keep: with its year (2026-09-03, "September 3rd 2019") it can give the date; without it ("the 3rd of September") it only confirms the model's date, never sets one. A bare "may" is the verb unless its year or a word like "on" or "since" comes with it. One phrase gives the date whatever the model gave; with two or more, the model's date must fall in one, and a not-sure one stays not sure. The model's text is read when the quote holds no phrase, but `as_said` comes only from his quote. A month after in, since, before, by, until or of stays that month, with no ends. Why: his words are the date, and a hedge filed at the day said is a fake point in an append-only record.
- **Ages and landmarks:** an age in explicit age context ("when I was 12", "twelve" or "twenty-five", "at age 12", "aged 12", "ages 12–14", "at 12 years old", and "in my teens" or "adolescence" as 12 to 18; never a bare "at 3" or "2–3"), its number ending the phrase (an end, punctuation, a conjunction or a pronoun; never "when I was 5 minutes into the run"), that the model's date doesn't rest on runs from that birthday to the day before the next one past it, as two ends with `as_said`; one that would start after the day said isn't an age, and files not sure. Where the record creates past events, a rough one ("about", "around", "roughly" or "maybe ten") runs a year either side ([threads](#threads)). The birthday comes from the `birth` landmark: `capture.landmarks` reads each slug's date from the store every run, from the firm entries (a date, no `approx`, no ends) carrying `landmark: <slug>` that head their chains (`units.corrected`: nothing revises or supersedes them). A restated date inside the other's span agrees and the finer wins; two that don't agree date nothing. Without a birth date an age files not sure, its words kept. The filer is shown each landmark with its date (the pack's `{landmarks}`). A fact the reply ties to one (`landmark: <slug>`) that his quote dates firmly (a phrase code reads, or a date written in it) is its dating entry; one his quote doesn't date, the model's day said included, takes the landmark's date (its day, month or year) with `approx`, `landmark` and `as_said`, padded when read ([search](search.md#periods-and-as-it-stood)), or files not sure, the slug kept, when the lookup dates none; one his own hedge dates keeps his date and no slug. The reply's `as_said` is kept only when code read no phrase and it's word for word in his own message. `engram add --landmark <slug>` writes a dating entry, and `--supersedes <id>` writes the `supersedes` link with it in the same commit, filed as `engram link` files it (the record's allowed rels, the day filed, the note "corrected"), which chains, the timeline's fold included, read. Why: a landmark is a life event with a known date, so a pinned memory, never firm, can't date one, and a linked correction re-dates it.
- **Dates never said:** code checks the model's date against the message and the question answered (`capture.said_date`): the day said, a day or span his date words name, a weekday or weekend named, a date written out, a month or year by name. Where the reply gives a fact's own when (`as_said`, word for word in his message) as a stretch up to the day he said it (`capture.stretches`: "the past week and a half", "the last 3 months", "past 2 days"), and its date is a day or month he never gave that lies wholly inside that stretch, the fact is filed as the stretch, the shortest that holds the date: its first day, `approx`, both ends, his words kept. A day, month or year he did give stands; a fact tied to a landmark keeps the landmark's rules; a date outside the stretch, or only overlapping it, is judged as any other. Why the reply must name it: a stretch frames a message, and code can't tell which of its facts the stretch is about; read as the date of every fact in it, it turned a day he named ("on the 3rd I fell") into a vague one. For the repeat check an entry with both ends, a stretch or any other span, is about every day between them (`capture.same_occurrence`), so a record dated inside it can be the same occurrence: its first day is no nearer the occurrence than its last. Any other day that fails narrows to the month or year that passes, else `date: not-sure`, as is a past one ("last time", "the other day", an "ago" code can't count) dated the day said or left undated, unless his date words name a day.
- **What it leaves out, told:** a reply may account for a line of the owner's it doesn't file (`left`: its line and why, as the sample's words ask for each of his lines, tooling talk being no record); each is a row of the run's `dropped`. Why: going through every line, the model keeps what he said of himself in a chat about the tools, and the run says what it didn't keep.
- **Kinds from the pack:** the filer offers the entry kinds its pack names (`kinds`), and files anything else as the first; a pack that names none offers the kinds the record already holds, most used first, with anything else an observation. Why: an area whose filer must write only one kind (a compiled area's sparks) can't be steered by what the record happens to hold; the fallback keeps a pinned pack's prompts as they are until its own pass names its kinds.
- **Placement when filed:** the same call returns each fact's threads, `occurrence_of` and `led_from`; code keeps only known threads (in a record that creates them, [threads](#threads) says which it's shown and what it may start), an existing occurrence page and an entry the record holds, with rels its `[links.timeline]` allows. No extra call.
- **A correction links to what it corrects:** a fact the reply says corrects an earlier entry (`corrects`, its id from the entries listed, the facts already filed or the search hits) keeps the id only if it's an entry nothing corrects yet. One low-effort call per correction (the pack's `correct_confirm`) sees that entry and what the owner said, never the first call's reasoning, and answers `slip`, `learned` or `no`. Either yes writes `supersedes` and its evidence link, noted with their words; anything else files the fact alone. A pack without those words files no links. Why: a wrong link pushes a true fact down with nobody watching, and a change since (a new dose, a better week) reads like a correction.
- **A slip is rewritten in place** (`capture.rewrite`, through `engram fix`) when the same session filed the entry, within 7 days, as the same kind; otherwise, or if the commit is refused, it's linked like any correction. The entry keeps its id, so its links to theory and evidence stay, when it was filed and, if the correction gives no date, its date; git keeps the old words. Why 7 days: coming back to a thread later reads as something learned. Why these limits: a wrong rewrite overwrites a true fact with nobody watching.
- **Theory changes:** the job files a status change (a stage too, and a new thing of the record's own kinds: [the theory's own kinds](#the-theorys-own-kinds-and-the-guides-suggestions)) or a theory link only when the owner states it or agrees to Claude's proposal, and keeps the guide's suggestions as the guide's; code drops an unknown id, status, rel or strength, a repeat, and anything not in the owner's words. When the owner agreed to a structural change, a second call writes the operations, and `plan()` checks them before `apply()`.
- **A thing's chain:** a change joins the chain its name matches (`now.chain_for`), strictest first: as written, strengths dropped, forms dropped, a prefix, then a name of two words or more inside a longer one. It's a repeat (`capture.entity_repeat`) only when that chain already stands at its status, with the same detail if he gave one: the chain's holds his, and any numbers he gave are the chain's, whole. Why that chain alone: one thing can sit on two chains, and a restart was dropped because the other still read active. A dropped fact's quote is kept in the run's log beside its headline.
- **Failures:** a reply with no JSON raises, so the session's mark stays; a summaries run that stops (the model unavailable) or a record summaries run that fails is the hourly run's error, and so is any job that raises or exits (`hourly.FAILED`: a re-check whose pack has no `relink` words exits, as a command would), the run going on to the rest and logging itself; a failed commit takes back what its transaction wrote; a failed push, or one that hangs past its timeout, is a row in `capture.sqlite`'s `push` table, shown at session start and retried hourly. `engram capture status` counts each session's entries from the store, and lists uncommitted entries, unpushed commits and a failing push; `engram capture refile <prefix>...` clears marks so the next run rereads a session.
- **Renewals,** a step after the filer and apart from it (`capture.renew`): a thing marked "last mentioned" ([shape](shape.md#identity)) clears when the owner says they're still on it. Code runs it only for a session where the owner, or Claude's message they answer, names a thing marked that day, generously (every form of its names, and each word of four letters or more); a session naming none makes no call. One low-effort call sees those exchanges (Claude's message cut to its end, where a question sits) and the marked things, in the pack's `renew` words, and answers per thing with the owner's quote or nothing. Code keeps one only for a thing marked that day, on an exchange that names it, with the quote word for word in the owner's message and any question answered in Claude's turn just before (`_his`); one a thing a session. It's filed as a `renewal` entry on the chain, which only the mark's date reads, and the filer's list of kinds leaves it out. A failed renewal is logged and leaves the mark. Why apart: teaching the filer to keep "still on it" changes what else it files.
- **Narrowing,** a step after filing (`narrow.run`), for an area whose pack has `narrow` and `narrow_confirm` words: a roughly dated entry narrows when a dated document turns up. It reads the documents the record gained since its mark (git additions under `[timeline] whole`), each dated by the index alone, once refreshed: the earliest `date` its sections hold. A date in a file's name is no date. A document's candidates are the entries dated roughly (`approx`, or two ends) that head their chains (`units.corrected`), whose range holds its date. One call per document with candidates asks which it records as happening on its own date, not only mentions or recounts, with the document's words for each; each yes, its words found in the document, goes to a second call (`narrow_confirm`: the entry, the document and its words, never the first call's reasoning), and only a yes is written. A candidate confirmed on one date gets, in one commit, a new entry with its whole front matter but its date keys, `heading`, `source` and `author`, at the document's date, with `supersedes`, `narrowed_by: <document>` and author `engram-capture`, and the `supersedes` link noted "narrowed by <document>", so the recollection stays attached as its older version. The copy keeps the recollection's `recorded`, and `now._chain` leaves out what a `narrowed_by` entry supersedes, so a tracked thing keeps its order and shows the document's date. A document is sent up to the sweep's limit (`relink.SWEEP_BUDGET`).
  - **What's counted and passed:** `undated`, a document the index gives no date; `unindexed`, one absent from a clean refresh (an empty file, a `.jsonl`, a PDF), which never will be read; `failed`, one whose reply held no readable answer, since a missed narrowing is harmless and the entry stays a range; `disagree`, a candidate confirmed on two dates, which isn't narrowed. They add up in `capture.sqlite`'s `narrow` row, shown by `engram capture status`, and each run's go to the job's log.
  - **The mark** moves to the head read, after the commit. A refresh that recorded an error, or a raised model error (quota, an outage), stops the run with nothing written and the mark unmoved, its spend still reported, and is the run's error. The first run marks the head and asks nothing, and a mark gone from history (a rollback) is reset to the head the same way and counted as `reset`.
  - **Why:** nothing here passes the owner, so a second call confirms, and the record's own documents are never narrowed in bulk.
- **In a repo with notes a chat starts from where the last session stopped** (`hourly.last_session`, for `[notes] stopped`): that section of the latest note whole, with the note's date, themes and path (its last lines, and where the rest is, past `notes.STOPPED_ROOM`), then a line for each entry recorded since the note was written (not its own session's), then, when the repo's latest other chat isn't filed through its end, one line naming it and `engram session <id>`, which prints it without tool calls or their output. These lines are printed whole, before the picture, which a cut takes first. The chat that's starting, resuming or being compacted is never that latest chat, and when the latest is an agent's (`sessions.by_agent`: a delegate or an executor in the repo or a worktree of it) or one the sessions state skips, nothing is said of it. It reads the capture state and the store, and of the chat files only that latest one, picked by when each was last written. Why: a session isn't saved until its pause has passed and the hourly job has run, and the next chat shouldn't have to be told where things stopped.
- **The session start fits whole:** Claude Code shows a SessionStart hook's output whole only up to 10,000 characters, a fixed limit; past it Claude gets a 2 KB preview and a file. The hook keeps to `hourly.HOOK_BUDGET` (9,000): its other lines are printed whole, and the picture gets what they leave, cut from its end at a line, with a pointer to `engram now`, which prints it uncut. So the picture puts first what a session needs first: upcoming, the theories and open questions, then where each followed thing stands and the team, and last the things stopped over a month ago, which a cut takes first. Why the cut: a long record's picture sits near the limit, and the margin is small.

## Setup

`engram setup <repo>`, for a repo whose rewiring is current, installs, idempotently, the session-start check (`engram capture check`), `Bash(engram:*)` in the allow list, a Bash window that fits engram's output (unless the repo sets one), the git pre-commit ([data model](data-model.md#the-pre-commit)) and the hourly job; `engram teardown <repo>` removes exactly those, restoring the settings file byte for byte; `engram capture status` (also in `engram health`) shows them, each session's last filing, the last repair and the job's last run. Every hourly run and session start repairs a missing or stale piece.
- **Teardown takes the run's lock** (`hourly.lock`), waiting if a run holds it, so a run started before can't commit into the repo after.
- **A launcher counts as current** when it imports this code (`setup.code_of()`), not when its path matches.
- **Claude's Bash window:** setup writes `bashOutputMaxChars` (`setup.BASH_BUDGET`, 100,000) into the repo's `.claude/settings.json` when the repo sets none, and only where it's set does the session start tell Claude to read engram's output whole, one engram command per Bash call. Why: Claude Code shows a Bash output whole only up to that window (30,000 characters unless set, 4,000 to 128,000), and a long record's timeline is past the default, so Claude would cut it or get a preview. The window holds for every Bash command in the repo, not only engram's, and costs tokens only when an output is that large; a project's value beats the owner's own global one there. A value the repo already has is kept at any size, and teardown drops only one setup added. Claude Code can override the setting remotely, per tool, with no sign, so a release checks that a long output still arrives whole ([operations](operations.md#the-release)).

## The instance lives in config

- **The code names no instance.** Whose record it is (`owner`), the domains, the archive's mirror, the second box the daily copy goes to (`[daily]`) and the folders of sessions rewiring reads (`[sessions] roots`, a mirror among them; Claude Code's own by default) come from the box's `~/.config/engram/config.toml`. A domain (`[domains.<name>]`) sets `repo`, `remotes`, `exclude`, `sessions_from` and `pack`; every one the config declares is served, in its order, and `general` is built in.
- **Dates are the owner's day:** `zone` in the config (an IANA name) becomes the process's time zone before any command runs (`config.use_zone`), so every date read off a clock (a message's day, the day "last night" counts back from, an entry's or a status's date, "today" at session start) is the owner's, and what engram starts inherits it. Why the process's zone and not a conversion at each call: one place covers every clock read, present and future. With none set the box's own zone stands; a name that isn't a zone is refused, since the process would read it as UTC.
- **`ENGRAM_CONFIG` names a file laid over the box's config,** table by table: a scratch copy or the frozen gate points a domain at its own clone and keeps the owner and the excludes.
- **Prompts name the owner from config.** A template writes `{owner}` and `{owner_id}` (the name in lower case, a record's `by`), and `config.voice` fills them.
- **The guardrails are engram's own hooks** (`.githooks/`). The pre-push refuses to send a public remote anything built on the private history, which only the remote named `archived` keeps. The pre-commit checks: no tracked `.venv`; the public tree (code, tests, docs, bench, skills, examples, README) names no instance on any line (the owner, their home folder, each configured repo's path and remotes), and `src/` no configured domain's name either; the tests pass; each pack the box pins passes its own tests at its pin; and under the weekly pass, nothing staged in what it may not change (below).

## Packs

An area's words and a few small functions live in its own record repo, under `.engram/`; core does the work ([shape](shape.md#a-pack)). Everything engram keeps in a record repo is in that one folder: the pack, the record's `engram.toml`, its git hooks, the weekly pass's specs (`specs/`), and one page, `README.md`: the owner's jobs, the area's decisions, its design when it has one, and how the weekly pass may change the repo, in that order. The pack runs from a pinned commit; `engram.toml` is read from the working tree (`paths.record_toml`), since `engram exclude` writes it.

- **What a pack holds** (`engram.pack.Pack`): `prompts`, the words of each model call engram makes for the area (`file`, `verify`, `record`, `renew`, `theory`, `structure`, `relink`, `relink_system`, `sweep`, `sweep_confirm`, `narrow`, `narrow_confirm`, `correct_confirm`, `recsum_system`, `compile`, `compile_post`, `compile_spark`, `health`); `kinds`, the entry kinds the filer may write; `current`, what "where things stand" follows (an entity kind and its statuses, detail field, never one engram writes itself (`store.WRITTEN`, refused at load), and name forms, thread prefixes and their sections, upcoming, the people seen); `occurrence_kinds`, where a repeat must be the same occurrence; `relink_skip`, the paths the evidence re-check never reads; `read`, a reader per source for what core can't read, and `on_request`, the sources too big to read before each search; `summary_rules`, what the session summarizer adds for the area, under its own version; `health`, a line on what's wrong between the repo and the pack. The theory graph, its revision and re-check, current, said, placement and the timeline stay in core as features any area gets.
- **A reader** gives the index's own records (`Doc`), the links among them (`revises`, `disagrees`; their family is the source's name) and the ways in they open. Core fills `{owner_id}` in an author and a date's sort key, cuts a long record into chunks, indexes each source under its name and rebuilds the ways in with the reader's. A source read on request gives records only: `engram ingest --source <name>`, or `all`. A file under a folder named in the record's `[index] spines` sits on the spine its subfolder names.
- **What isn't in a pack:** an area with no `file` words is searched, never filed for: `engram setup` refuses, and `file_session` raises. With no `current`, `engram now` shows only what the theory graph and the people list give. Recurring-thread pages come from the record's `[ways.symptom] pages`.
- **The pin's tree** (`pack.tree`) is the id of `.engram/` without the page, `specs/`, `engram.toml` and `hooks/`: those change while the pack doesn't, and the gate and a release compare only what runs.
- **Loading.** `[domains.<name>] pack` is a commit of the record repo or an absolute directory (a worktree, a scratch clone, a test). A commit is extracted once with `git archive` into `~/.local/share/engram/packs/<name>/<commit>/`, read-only, through a temporary folder renamed into place, so parallel readers never see half a pack. It's imported as `engram_pack_<name>`. Nothing in the record's working tree runs: a commit there is inert until it's gated and pinned.
- **The owner's words leave out every session an agent started** (`sessions.by_agent`), for rewiring's turns, check's any-session quotes and the weekly pass alike: a headless run, or a first message that opens with one of the openers a harness puts before a delegated brief, as the harness writes it whole (`sessions.AGENT_OPENERS`: "Act as the <role> sub-agent for this task.", never "Act as the" alone, which the owner may type); a brief is judged message by message (the weekly pass, rewiring's turns), and the filer and summaries use the same session rule. A delegate's report and an agent's hand-back are never turns. Why the opener: nothing structural tells a delegated session from the owner's own (same entrypoint, worktree and permission mode).
- **Drift is judged on what's committed.** `[rewire] at` is the id of the jobs and failures a rewiring answered (each item's bold name and its quotes), not a commit: a commit can't name itself, so the commit that changes the jobs moves `at` with them. Prose around the items, or elsewhere on the page, isn't drift. `engram rewire check --drift` reads the index (inside a hook, the one git names), HEAD and, in a conflicted merge, MERGE_HEAD, and refuses only the signs the index has and neither of those does, so the pre-commit judges the commit being made: drift that reached HEAD another way (a pull, a `--no-verify` commit, a release whose copy detection finds more) is `engram health`'s to show, and never stops a commit, the filer's included. It skips the history scan, so it runs on every commit unnoticed.
- **Isolation.** A pack may import only the standard library, pyyaml and `engram.pack`, checked before it's imported. One that fails to load is its domain's alone: nothing is filed for it and its `current` rows stay as last indexed; `engram health` and the session-start hook say why. `.engram/` is in every domain's index excludes, and the loader reads only its Python files.
- **Tests.** An area's behaviour is tested in its pack's `tests/`, which run with engram: `uv run pytest <repo>/.engram/tests`. Core's tests file through `examples/notes/`, a small made-up area whose pack sets only words.
- **Left in core:** the canon's vocabulary that the summaries' format and the index already speak (story, complaint and series prefixes, clinician labels, the summarizer's base prompt and its examples, whose move would change the prompt's bytes and so needs a versioned summary QA), and waysin's treatment builders and its pooled-series name.

## Notes

`notes.py`, for the owner's call that a session note is part of the record, in a repo whose `.engram/engram.toml` has `[notes]` (`folder`; `sections`, each a `name` and whose words go in it, `by`: `owner`, `guide` or `guide unanswered`; `line_words`) and `[sessions] pause`, and whose pack has `note` words. Without all three the filer reads a chat whole, as it always has.
- **Sessions:** a chat splits at a silence of `pause` minutes or more after an exchange's last row, and the hourly job takes a chat once its last message is `pause` old, not an hour, so a session is saved once, after it ends. A session is known by its chat and its first message's id (`start`): a chat rewritten by a rewind or a compaction keeps its sessions, and one with a note is never asked about again. Why the first message's id: lines and bytes move when the file is rewritten, the id doesn't.
- **One call per session,** in order: the filer's own call over that session's conversation alone, with the pack's `note` words after it (the lines it covers, the sections and whose words each takes, the five latest notes). The reply adds `working` and `note` (`sections`: name → lines of `line`, `quote`, `by`; `about`; `follows`). Why the same call: the facts and the note are read from the same words, and a second call would read them twice.
- **Code checks every line** (`notes.check`): its quote, as whole words, in the owner's message at that line or one of the guide's replies to it, whoever the reply credits. A line in neither refuses the whole note, as does a note with none of the owner's words; a line of the guide's in a section only the owner's words go in is left out, so the guide's "that sounds lighter" never reads as what changed; in a section of what he didn't answer (`guide unanswered` without `guide`), a guide's line with a message of his after it in the session is left out, so a chat never starts from an offer he already took up or turned down; and a section left with nothing reads "not said". Why refuse the whole note: one invented line under the owner's name means the call misread the session. A line names its speaker and its line of the chat; an owner's line after a guide's turn that ends in a question has that question beside it; the owner's lines are whole, of any length; past `line_words` a line of the guide's is kept by its opening words, the question beside a reply by its closing ones.
- **A refused note holds its session:** nothing from it is filed and the chat's mark stays before it, so the next run asks once more; refused again, its facts are filed as for any session and it's summarized (`capture.sqlite`'s `note` table counts). Why hold rather than file the facts first: filed beside a note there are fewer of them (below).
- **A note** is `<folder>/YYYY/MM/<id>.md`, its id from the session's first message's time (`YYYYMMDD-HHMMSS-note-<hash4>`), with front matter `id`, `date` (the session's first day, in the owner's zone), `chat`, `start`, `lines` (its first and last line of the chat file: every line is in one session), `follows` (the chat's previous note), `continues` (a recent note of another chat it carries on, when the reply names one) and `about` (the reply's, of values the record holds, and those of every fact it states, threads that fact started included), and a `## <section>` each. It's written in the filer's transaction with the session's facts, committed and pushed, created only where no file is, and the record's pre-commit refuses an edit to one as to an entry.
- **What the note states isn't filed again:** a fact on a line the note cites as the owner's is left out, unless it's of the tracked kind (a practice); every fact filed beside the note carries `note: <id>`. Why: the note stands for the session, and an entry beside it would show the same words twice.
- **No summary beside it:** a summary leaves out the lines a note holds (`notes.held`), so a chat whose sessions all have notes has none; a session that wasn't a working one is summarized as always.
- **A correction of a note** (`corrects`: its id) is filed with a `corrects` link and no confirming call, and search shows it under the note as "corrected by", even when it's a hit itself. Why not `revises`: a correction of one detail doesn't replace the note, so the note stays the hit.
- **In the index a note is one record,** read whole (ref `<path>#`): a hit on any of its lines is the note.

## Threads

A thread is an `about` value entries sit on (`threads.py`). A story is one in any record; a record whose `[threads] create` names kinds (the sample's: theme, person, event) lets the filer start one of them.

- **Started only from his words:** a fact's `create` (kind, name) is kept when the record creates that kind and the name is whole words of the message the fact quotes; the thread's id is its kind and that name slugged (`person/my-dad`), and an entry of kind `thread` holds the name as he typed it. A name a thread already goes by is that thread. A past event (`event`) must be dated, by the date its entry takes, no later than the day he said it. A theme (`theme`) a fact starts gathers the earlier entries the fact tells again (its `again`) that are on no theme; one already started gathers nothing. A refused create is a row of the run's `dropped`, and the fact is filed anyway. Why his words: a name the filer chose would be a claim about him he never made. Why only entries on no theme: putting what's on one theme onto another is a join, and joins are his.
- **Found by his words and what's recent:** the filer is shown, each with its names, the threads his words name (any of a thread's names, whole words), those the search of his words hit entries on, those of the entries dated around when he spoke, then the 80 most used; a fact may be on any thread the record holds. Why: a most-used list leaves out a thread he names but seldom used; an ended one is shown with the day it ended.
- **A second name, a move, a gathering:** `names` (thread → name) adds a `thread` entry with another of his names for it; `moves` (entry, from, to, `said`) writes a `placed-on` link that takes the entry off the wrong thread and puts it on the right one, a new one named as a create is, when `said` is his words in that message saying it was wrong. Nothing is edited, so nothing is lost. Why his words: a move undoes where something was put, and only his saying so is a reason the record can show.
- **Joins, splits and ends are the owner's:** the filer refuses every `thread_ops` it's given, each a row of `dropped`. The dated links `joined-into`, `split-into` and `ended` come from a conversation (`engram link`). Why: only the conversation knows the reason for one.
- **Read where the index is built:** an entry or a note is on its own threads, as `placed-on` links moved it, plus every thread joined to one of those and every thread split from one after its date (`Threads.on`), so a history, search's thread votes and `engram now` agree. These links and the names are read only where the record creates threads. Why: a record that doesn't may already allow those rels, and its first such link would change its histories.
- **Asked for by any name:** a created thread is a way in by each of its names, however long, lighting what's on it and never mere mentions (`waysin.LINKED`; "dad" is an everyday word), so `timeline.chain` finds it by its id or a name, and a name two threads share finds both. A note in it lists the entries filed with it (`with-note`, from each entry's `note`), which leave the rows.
- **Where things stand:** a created kind in the pack's `current.threads` shows each such thread in its section, by its first name, with the latest thing said on it in his words.
- **No page to render into:** a fact with no thread stays on none, rather than taking the most used one as a record whose entries render into pages needs.
- **A past event with a rough date** keeps his words and a range: "when I was about ten" runs from his ninth birthday to the day before his twelfth (the filer's ages).

## The theory's own kinds and the guide's suggestions

A record may add its own kinds of theory thing beside node, state and loop (`[theory.kinds.<kind>]`, the sample's belief, part and insight): each a `folder` of thread files, and for a change made gradually (an insight) its `stages`, how far along it is, and `needs_note`. `theory.kinds` is the one lookup: `theory.load` reads each kind's folder, `theory.file_for` says where a new one goes, for the filer and for `engram theory change --add-node` alike, and a record naming none keeps the theory it has. Why one lookup: a second path for the record's own kinds would drift from the built-in one.
- **Two labels on a thing:** its status (`theory.STATUSES`), and for a kind with stages its stage, each the latest status entry that sets it (`status`, `stage`, or both). One never moves the other. The filer sets a stage, like a status, only from the owner's words or his agreement, and only one of its kind's stages. Why apart: how sure an insight is and how far the change has got move at different times.
- **A thing he names:** a theory item's `add` (kind, id, name) is filed when the kind is the record's own, the id is `<kind>/<name>` and unused, and the name is whole words of the message his quote is from; its file is his. A kind that `needs_note` is added only from a session whose note is written this run, and its file names the note. Why: a name the filer chose would be a claim about him, and an insight is worth keeping where the session it came from can be read.
- **The guide's suggestions,** where the pack has `suggest` words (they follow the theory words in the filer's prompt): the reply's `suggestions` are the guide's ideas about him that he hasn't agreed to. Code keeps one only when its quote is whole words of the guide's message on its line (a reply's own line, or the line of the owner's message it answers, as the conversation shows them), past the filed mark, and it's a new thing of one of the record's own kinds (its id unused: the same suggestion again, or one the theory holds, is a repeat) or a join between two things the theory holds. It never carries a status or a stage, and never adds, removes or reorders a loop's step: those are his. A new one is a file in its kind's folder, `by: claude-suggestion`, its `quote` the guide's words and its heading labelled the guide's, and a `proposed` status entry by `claude-suggestion`; a join is a theory link by `claude-suggestion`. Adding one queues no re-check of the record (`theorychange` isn't called). Why: a suggestion written as his would be the guide's words saved under his name, and a re-check for an idea he hasn't taken up spends money on a guess.
- **What he says of one** is a theory item on it, in his words, naming what he does with it (`on`, `says`: adopts, denies, agrees when asked, doubts, asks; `capture.spoken`): his own words for it make it provisional ("adopted"), a denial rules it out, and a doubt or a question changes nothing, whatever status the reply also gives (a status item is read as before); the status entry keeps his words (`said`) and any question he answered (`answering`). A reply of under three words (`capture.SHORT`) never adopts one: with the question it answered it's kept as an entry on the suggestion, headline and body the question and his reply, and its status stays; without one it's dropped. When he speaks of one in the session it was made, its `proposed` entry isn't written, the file keeping the guide's words, and in one second the guide's entry sorts before his (`theory.load`). Why: "yeah" to the guide's guess is the guide's guess, and a reply that must say which of these it is doesn't slide from "I don't know about that" to a no; and a status read from two entries of one second would be a coin toss.
- **Labelled the guide's wherever it shows** (`theory.who`: "the guide's suggestion" with its quote, then "raised by the guide, adopted by <owner>" with his words): `engram theory`'s table of the record's own kinds, the picture a chat starts with, a history's theory block for a thing asked for by its id, its page in search (the heading, and its front matter's section, `sources.sections`), the filer's theory block and the sweep's targets. Why: a theory full of suggestions mustn't read as settled.
- **The picture a chat starts with** (`now.own_theory`) lists the record's own kinds, without what's ruled out or replaced, and without a suggestion still proposed that he hasn't spoken of (an entry of his on it) for `[suggestions] quiet_days` since it was made; moments linked to it and the guide saying it again don't count. `engram theory` shows them all.
- **A short yes in his voice:** where suggestions are kept (the pack has `suggest` words) or stated beliefs are, whether or not the theory holds anything yet, any fact filed from a reply of under three words to a question is headlined and opened with the question and his reply (its `answering` kept), and one with no question with his words alone, never the model's statement of it: "yeah" to "is that shame?" isn't "feels shame".
- **In conversation,** `engram theory change --status` on a suggestion he hasn't spoken of needs his words (`--said`), which its status entry keeps.
- **The linking job** shows the record's own kinds among its targets, each labelled, and links to what the record's link kinds point at ([the evidence sweep](#the-evidence-sweep)).

## Stated beliefs

A record may keep what the owner says about himself as a trail (`[beliefs]`, `beliefs.py`): `kind`, the entry kind a stated belief is saved as; `belief`, the theory kind a statement links to (a group of statements that say nearly the same thing); `rel`, the record's own moment link kind it links by ([the evidence sweep](#the-evidence-sweep)); `under`, the theory link that puts a belief under a broader one. The sample's are stated-belief, belief, showed-up and under. A record that names no `kind`, or whose pack has no `stated` words, saves nothing differently. Why these four and no store of its own: a stated belief is an entry, a belief a theory thing, its link a moment link and a category a theory join, so a trail is a walk of links the record already keeps.
- **Filed with its context:** a fact of that kind keeps his words as he typed them (`said`, the quote's span of his message), `context` (the guide's turn just before his words, taken from the chat, `capture.turn_before`, never from the reply) and `chat` (the chat's id), beside its date, threads and source. Why: what was being said at the time is what makes a trail read as more than a list of quotes.
- **Linked by meaning:** the filer is shown, after the theory words and the pack's `stated` words, each belief of his (`beliefs.his`: one he named, or a guide's suggestion he adopted) not ruled out or replaced: its id and name, whose it was when the guide raised it (`theory.who`), what it sits under (each the guide's where it is, and an `under` the guide suggested marked so), and his latest three statements linked to it (`SHOWN`), each by its first 200 characters. The reply's `beliefs` (id, `loose`) are each kept when the id is a belief of his the theory holds, not ruled out or replaced, and `rel` may point at that kind; a belief still the guide's is neither shown nor linked to. Why: it's the guide's idea of him, not a group of his statements, and he makes it his by adopting it; linked to, its trail would read as backed by him; there is no limit on how many, and none of the filer's three-thread cap. `loose` is marked on the link. Each refusal is a row of `dropped`. Links are by=claude, author `engram-capture`, Claude's placement. Why shown statements, not search: statements that mean the same thing share no words, so keywords can't find the group, and a few of his statements say what a belief holds better than its name.
- **Each time he says it:** the repeat check keeps a stated belief said on another day as a new occurrence (its kind is one of the pack's `occurrence_kinds` for the call), so a statement he made before, or the belief page that quotes it, never stops it. Why: a trail is every time he said it.
- **A new belief** (`new_belief`, a name) is kept when the name is whole words of his statement: its id is `<belief>/<the name slugged>` (one the theory holds is that one), its file is his, in the kind's folder, and the statement links to it. Why: a name the filer chose would be a claim about him he never made.
- **A short reply is no stated belief:** a statement of under three words (`capture.SHORT`) right after the guide's turn is filed as the pack's first kind, the question and his reply kept, never as a stated belief in his voice. Why: "yeah" to "you feel like a burden" is the guide's belief, not his.
- **Beside a note:** a stated belief a working session's note also holds is kept beside the note (`note`), as a practice's change is. Why: the trail must hold what he says in a working session, where most of it is said.
- **The trail** (`engram theory trail <belief>`, `beliefs.trail`): every statement linked by `rel` to the belief or to any belief under it at any depth (a belief may sit under several), each once, oldest first, never ranked. The header names the belief and whose it is, the beliefs under it (each the guide's where it is, and an `under` the guide suggested marked so), how many statements there are and how many are `left`; each row has the id, date, his words (`said`), `context` (its last 400 characters), chat and threads, `via` (the beliefs under it the statement is linked by), `loose` when every one of its links here is, and `linked by` the guide's suggestion when each is the guide's. Past the Bash window (as [the timeline](search.md#the-one-call-timeline) reads it) it prints as many rows as fit, and the header's `more` gives the command for the rest (`--skip N`). Why whole: a trail is read as a batch, and a top five would hide that a belief keeps coming back.
- **A regroup** (`engram theory regroup`, `beliefs.regroup`, for a look-back): one call at medium effort reads every stated belief with the beliefs it is linked to, and the beliefs, in the pack's `regroup` words, and proposes new beliefs, new links and broader beliefs to sit under. It only adds: a removal is refused, and so are a link already held, a target that isn't a belief, a belief put under itself or under what sits under it. Everything it adds is the guide's suggestion (`by: claude-suggestion`, author `engram-regroup`): a new belief is a file labelled the guide's with a `proposed` status entry, named from a statement of his when the reply says which and the name is in it, else named by the guide. One commit. Why one call and no embeddings: at a few thousand statements every one fits one read, and the filer already groups each by meaning as it saves it.

## What a practice follows

The pack's `current` says what "where things stand" follows, and four of its fields replace what was built in: `ongoing` and `finished`, the statuses of a thing still going and of one stopped (else a medication's: taking, prn, active; stopped, done, concluded and the rest); `whole_names`, a name kept whole, never split at a bracket into brand and generic and a way in at any length (else split, and at most four words); and `origin`, the theory kind an entity entry starting a chain must name (its `origin`, an id of that kind the theory holds) to be followed; a later change joins the chain without one. One that names none, or one the theory doesn't hold, is filed as the pack's first kind, his words kept, with a row of `dropped` saying why. Why: a practice that came from no insight is something he said, not a thing to follow; and a practice is said by its whole name, which four words of it don't make.

## The compiled wiki

`intake.py`, `compile.py`, `wiki.py`, for the owner's calls that knowledge needing ingesting is compiled and that its wiki is a traditional one, of concept articles ([data model](data-model.md#sources-sparks-and-the-wiki)).

- **Intake** fetches a page with the standard library and reads it to text by `html.parser`, keeping the URL; a video or an image arrives as the advisor's reading, marked `transcribed_by`, with the file kept by its sha256 under `events/files/`, which the append-only check already guards. Why sources are entries and not a new store: entries already carry title, author and date, so a hit mid-article shows who said it.
- **One page model** (`wiki.Concept`, `wiki.Source`): a page's properties and sections as typed data, rendered to Obsidian markdown and parsed back byte for byte; the checker, the splicer, the index and the health check all read it. Why: the model's edits are data that code applies, so everything outside an edit stays as it was, and that's checked rather than hoped for from a model rewriting a page.
- **Compile:** one Opus-low call per item, in the pack's words (`compile` for a source, `compile_post`, `compile_spark`), given the item and every concept's first sentence and numbered steelmans. A source's reply names at most five concepts it bears on, each with the source's words, its position, steelmans and answers, plus the source's summary and key quotes; a post's sets its line under "In your writing" and may revise a summary, answer a steelman or bring a new concept; a spark's names the one concept it bears on, and code writes the spark verbatim there and on the source that set it off. Code splices the edits into the pages as HEAD holds them: an old entry is never rewritten, a summary changes only on a post or a spark (or a new concept), and a `[[Name]]` the model writes becomes that concept's link, or its plain words when no such concept is there. Why one call per item for all its concepts: the item's text is sent once.
- **The checker** (`wiki.check_concept`, `check_source`, `kept`): properties and sections as the model says; every quote word for word (`verbatim.found`) in what it cites, a spark's in a spark, a source's summary sentences as recsum checks one; every link resolving as Obsidian resolves it, against `.md` files, or to a page made in the same compile; a steelman from a source quoting it, one of Claude's own quoting nothing; an answer quoting what it links, else it counts as unanswered; a source's position one short sentence after its words; everything outside the edits byte-identical. A failing page is asked for once more with its problems, then parked as (item, concept) in `open.md` while the pages that pass land, links to it taken out of them. A source page that fails fails the item.
- **Commits:** one per compiled item through `Store.transaction`, its pages as the paths, and the compiler writes only under `wiki/`. Its commits carry `ENGRAM_WIKI`; the pre-commit refuses any other change under `wiki/`, naming the paths and the one command that puts them back, and refuses `[[` or `> [!` added to the folders `[wiki] plain` names. Why commit the wiki: it's written work, costly to write again, and git keeps its history.
- **What was compiled** is the data folder's (`compile/<domain>.json`, by item and text hash, with the parked pages and the health check's findings): a source or spark is compiled at once and once, a draft once its text has stood a day unchanged in git (a pure rename isn't a change), a post at once when it's published, and an item whose call fails twice at the same text is parked until it changes. One run per area at a time (`compile/<domain>.lock`). The hourly job compiles what's due; `engram source add` compiles its item before it returns.
- **A moved post:** a post gets its stable id at its first compile, the pre-commit records any move git sees of a document with an id, and each run first points the wiki's links to a moved post where the registry says it went, by code.
- **The index and the open list** are written by code from the pages at the end of each run and health check, committed when they change; a rebuild is byte-identical. The index lists the concepts by pillar, each with its summary's first sentence, its sources, its steelmans and how many are unanswered, and, while no post uses it, its sparks (a post to write); then the sparks no concept has taken and the latest sources. The open list holds what couldn't be compiled or hasn't been, the parked pages, links that go nowhere, answers that no longer check, concepts nothing links to, and the health check's findings.
- **The health check** (`engram wiki check`, and after each repo's weekly pass, its cost the pass's): one call over every concept's summary and the sparks no concept has taken. Merges are applied by code: the kept page takes the other's name as an alias, everything the other held is appended, and every link is repointed. Splits, contradictions, a concept for three or more sparks that share a thread, and gaps wait in `open.md`; nothing is fetched until the owner says go. Why only merges are applied: a merge loses nothing and its alias keeps the old name working, while a split needs new prose.
- **Quote matching** (`verbatim.norm`) treats every dash as one hyphen, an ellipsis as three dots, and a word hyphenated across a line as one word. Why: page text and transcripts break words and dashes where the model's copy doesn't. A quote counts only as whole words (`verbatim.inside`, which the summaries' lint uses too): "no" is no quote of "I know", nor "mm" of "summer".
- **A thin repo's jobs:** `engram rewire turns --session <id>` adds the owner's turns from a jobs interview held elsewhere, so a repo the owner hands things to more than talks in can cite them.

## Building without touching what runs

- **The hourly job runs from a release checkout at a tag** ([operations](operations.md#the-release)). The tag moves forward only when the frozen gate passes; rollback is moving the tag back. Builders work in worktrees. Why: an editable install would make any merge live within the hour, in a job that commits and pushes a record.
- **Only the release repairs the box's install** (`setup.refused`, shared by setup, every repair and the daily and weekly jobs' installs). Once the box's own data folder has a loaded install, an engram running from anywhere but the release clone (when there is one) sets up and repairs nothing and installs no job; under another `ENGRAM_DATA` no job is written or loaded, and a repo the real install serves keeps its settings and hooks. A piece left alone isn't a repair, so it records none. Why: else a worktree's or a scratch copy's engram repoints the real repos, job and rows at itself.
- **Index changes are additive.** New columns are nullable, added by `ALTER TABLE` in one change, after the `.sqlite` files are copied; once every index and usage log has one, it moves into the schema and the upgrade step goes. A rebuild from source would drop sessions older than Claude Code keeps, which survive only in the index and the session mirror, so the rebuild drill uses the mirror.
- **Commit messages engram writes come from fixed templates** (`commitmsg.TEMPLATES`). In the hourly path an amount the figure check finds (`figures`: a whole number read with its money, magnitude, percent or share marks) is stripped, not refused: a refusal rolls back the filing transaction, and it would fail again every hour.

## Scratch copies

- A scratch copy is evaluated with `ENGRAM_DATA=<copy>/data ENGRAM_CONFIG=<copy>/config.toml`.
- **A scratch index stays frozen:** searches skip the automatic refresh when `ENGRAM_FROZEN` is set or the data folder is under `scratch/`. Why: a refresh would pull new sessions into a scratch index and move its results.
- The real record is untouched until the before-and-after review, and changes land as reviewable per-file commits.
- **`ENGRAM_SANDBOX=1`** keeps commits local and skips pushing. Eval runs set it. Index and usage rows still go to the data folder in use, so set `ENGRAM_DATA` to keep a probe out of the real logs.

## A vault's default rule

Which tags are threads when the owner hasn't said (`vault._stories`): a tag is a thread unless it's on more than 90 sections, or on more than 5% of the notes and at least 40; and it joins at least two notes. A dated section with no thread of its own takes the most specific threads of the notes it links to, as far as each has room. The owner's `story` overrides all of it. Why:
- **A timeline is read whole,** and engram's assumes a thread of dozens of rows; a tag like `#book` is a category of hundreds. The cap of 90 leaves room for the corrections a timeline brings in, under the 100 rows a one-tag timeline may run to. `tests/test_vault.py` holds it on an 8,000-note made-up vault and, given `ENGRAM_PUBLIC_VAULT`, on a public vault at a pinned commit.
- **Only a dated section borrows.** A daily note's line is an event on the story it links to; a wiki page linking to a note is reached through that note's backlinks anyway, and on a real vault its borrowing filled a status tag with pages that were on no story.
- **A tag on one note isn't a story:** the note's name reaches it, and each such tag is one more thread a free-text question could merge.
- **The floor of 40 notes is for small vaults,** where a real story can pass 5%: taking a category for a thread costs a short timeline, and taking a story for a category loses it.
- **A note linked by more than 90 sections lights only its own,** for the same reason: on a real vault, naming a hub note brought hundreds of rows. Search still finds the best of its linkers by their words.

## The weekly refinement

`refine.py`, for the owner's call that a weekly pass refines engram and each repo it serves.

- **Which repos:** engram's own (`[refine] repo` in the config), then every configured domain's that has its page (`.engram/README.md`); one with `[refine] paused = true` in its `engram.toml` is skipped. No separate list: a repo engram owns is one the pass serves. Why the page: it's what the pass answers to, and a folder configured only for search has none, so it gets no specs.
- **The pass** is `claude -p` handed `skills/engram-refine/SKILL.md` by its path in engram's own repo, so an edit there steers the next pass without a release. It runs in the data folder's `scratch/refine/`, outside every repo, so no repo's session-start hook or filer sees it.
- **The pass runs engram fenced** (`refine.fenced`, in the pass's env): `ENGRAM_DATA` is a copy of the data folder (each SQLite file, the value review's too, through SQLite's backup, and the moved refs) in `scratch/refine-data/<week>-<repo>/`, cleared at the next pass's start, with capture's repo rows dropped so nothing run there serves a real repo; `ENGRAM_GATE` is the real gate folder, for the baseline; `ENGRAM_CONFIG` lays a `repo` over the box's config for the domain under pass only and `repo = ""` for every other (all of them on engram's own pass), the shape the gate's freeze writes. engram's `.githooks/packs.py` and `instance.py` drop `ENGRAM_CONFIG` and read the box's own config, so the pass's commits in engram are checked as anyone's. The fence covers what finds a repo through the config: `theory change`, `recheck` and `sweep` by `--domain`, and the wiki's domain lookup. `add`, `link`, `exclude`, `source add`, `nodes prune`, `fix`, `wiki`, `moved` and `docs` take `--repo` or the cwd, and Bash and git are outside it: it guards against accidents, and adds no more machinery. Under it engram's own pass can't `show`, `now` or `theory` another repo's records; its evidence is the conversations and the value review's findings. Why: a pass is given one repo, and the data folder and the other repos are the owner's live record.
- **What the pass may not change in engram's own repo** (`refine.OFF_LIMITS`): `bench/gate.py`, `skills/engram-refine/`, `.githooks/` and `src/engram/landing.py`. The pass's env carries `ENGRAM_REFINE`, under which engram's pre-commit refuses a staged change to any of them (`claude -p` passes its env to the `git commit` it runs, and the refusing hook is the worktree's own copy, hence `.githooks/` on the list), and its settings deny `Edit` and `Write` on them. It guards against accidents: `--no-verify` and the fast-forward merge skip the hook, and a Bash write passes the deny rules (the hook still catches its commit). An approved spec that names one of them is built in a session, on a `refinement/` branch through `engram refine review` and `land`; the pass leaves it `approved` with `blocked:` saying so, as an outcome. Why: the gate measures the pass, the skill steers it, and the hooks check it, so a pass changing them would grade itself.
- **Every change lands through a fresh review** (`landing.py`), for the owner's call that nothing lands unreviewed at any size. `engram refine review <worktree>` hands the committed diff, the line the owner would be told and where the rules are to one `claude -p` that can only read, from outside every repo, under `landing.CAP`; a reply that isn't a clear pass doesn't pass, and it counts as a round. Each branch gets two (`landing.ROUNDS`): the second sees the first's findings, to check they're fixed at the root, and reviews the whole change again. `engram refine land <worktree>` is the only landing: it refuses a diff or owner's line no review passed, by a mark of both that counts every byte of the diff but not its place in the file, so a fix needs its review and a rebase that leaves the diff alone doesn't, then merges, clears the worktree and pushes, so a merge that can't apply leaves nothing done and a failed push waits for the repo's next. A branch that only adds new open specs lands with no review: it changes nothing until the owner says yes, and the build is reviewed then. Any other change to a spec is reviewed, since a status or an approved plan moves what the yes covers, and `--spec` takes only one the repo's own copy says is approved. Reviews and landings are `refine/reviews.jsonl`, the real folder under a pass (`ENGRAM_REFINE` names it); their cost counts toward the week, outside the pass's own `--max-budget-usd`, and a review the week can't pay for is refused, so the change becomes a spec. A running pass's own spend is left out of that check, since its row holds its whole cap and may be all the week has left, so a week can pass its cap by at most what that pass spends. It guards against accident as the off-limits paths do: the pass's settings deny `git merge`, and the check at its end reads what carries a `Refinement:` line, so a commit made straight on the branch with none goes unseen among the owner's and the filer's. Why code rather than the skill's word: the author chose its reviewer's brief before, and could skip it.
- **A pass can't wait:** its env disables background work and holds a Bash call open past a review's limit, and its settings deny `Monitor` and `ScheduleWakeup`. Why: `claude -p` ends with its turn, so a pass that started a review or check in the background and ended its turn to wait dropped the work and reported success.
- **"Apply" is a build on request** (`engram refine run --repo <name> --approved`, `mode=approved` in the skill), for the owner's call that a spec answered in a session takes the same review: only the approved specs get built, with no sweep, health check or page. Its ledger row (`job: build`) counts toward the week and fails as a pass does, but never stands in for the week's pass, and its changes and failures reach the next page. Why: a full pass would land changes the owner didn't ask for just then, and could take the week's pass's place.
- **A pass that says it's fine is read back from the repo** (`refine._unfinished`): an approved spec it neither built nor marked `blocked:`, a `refinement/` branch still standing, or a `Refinement:` commit with no logged landing makes the pass failed, whatever it reported. A failed pass is one plain line on the next page that gets written, however late, as well as in `engram health`, and marked shown in `seen.json` as a change is, since a failure no page names is one the owner never hears of; this week's free failure waits, as a catch-up tries it again. It keeps the usual retry rule, so its work waits for next week's pass, which picks up a worktree it finds.
- **What it tells the owner** travels with the change: every landed commit carries a `Refinement:` trailer, its line, and one the owner wouldn't see opens it with `none:`, which keeps it off their page; `.engram/specs/` holds what waits on them, and an approved spec a pass couldn't build says why in `blocked:`; one still approved with no reason, as a pass cut off leaves it, shows too, so work they said yes to can't fall silent. After a run's passes, unless none ran or a dry run, `digest` reads both from git and the working tree of every repo the pass serves; when anything waits (a pass that failed, an open spec, an approved one not yet built, a change they'd see not yet on a page, jobs still proposed), one `claude -p` with no tools turns them into the week's one self-contained HTML page, `refine/digests/<week>.html` in the data folder, each item under its repo, which opens in the browser, and only once it opens are its changes marked shown in `refine/seen.json`. A box that can't open it (only macOS's `open` does; a server has no screen) marks nothing shown, `engram health` names the page, and no later page is written until its items change (`refine/unshown.json`). Why: a page marked shown that no one saw would drop its items unseen. When nothing waits, nothing is written or opened. The run's report names the page, and a run later in a week that has its page leaves its items for the next. So a revert takes the line with it, no file of notes can drift from what landed, and a page that fails leaves its items for the next. It runs in the run's own process, which no session holds, and its cost (up to `DIGEST_CAP`) is its own ledger row (`job: page`), within the week's cap. Why one page a week, and only when something needs the owner: it's for reading, not acting, and the owner answers each item in a session in its repo, which reads the specs from disk; never at session start.
- **A deferred spec** (`status: deferred`) is on no page, and no pass builds or re-specs it, until the owner raises it again. Why: the owner put it off; showing it each week would ask again.
- **Session start** (`engram refine surface`, from a set-up repo's `engram capture check` or a read-only repo's own hook) shows only, for the agent, a spec or page here or in engram's own repo whose front matter won't parse. Why: a session's edit is how one breaks, and a broken one drops off the page unseen.
- **Spend:** each pass's cost goes to `refine/ledger.jsonl` by week (from Saturday, so the Sunday and Monday catch-ups count in it); an unreadable result counts as the pass's whole cap, as does a pass that times out at `[refine] hours`; one that never starts costs nothing.
- **A pass's cost is written before it starts,** at its cap, and replaced when it ends: a pass stopped mid-run keeps its cap spent, so nothing reruns it for free. A pass that failed at a cost is the week's; one that failed for under $1 (as when it never started) is retried at the catch-ups. A pass on request (`engram refine run --repo`) first checks the repo isn't paused, the week's cap isn't spent and no pass is running, says why if one is, and then starts on its own, kept awake, so no session's time limit cuts it off. The schedule waits out a pass that holds the lock rather than giving up its firing. Why: a pass may run for hours, and a session stops its background commands within two. A failure is told in `engram health`, never at session start: the owner reads outcomes. Why: a pass that fails the same way each time would otherwise spend the week's budget again and again.

## The value review

`review.py`, for the owner's call that every repo on engram can call a review of engram's value (in the private `.engram/README.md`).

- **When:** in the hourly job, for a session idle an hour, at most one a day per repo, in a repo whose `engram.toml` sets `[review] on = true`; on demand, `engram review <session>`. Off by default.
- **What it reads:** one Opus call at high effort with no tools. For each of the owner's asks: their words, each engram call the advisor made with what it returned, the answer, and engram's own first call on their words as of the session's day.
- **What it returns:** findings as JSON, each with its question (`data`, `path`, `balance`), the ref, the call that should have surfaced it, what was missed, and its cause: `advisor` (a call returned it), `tools` (the record held it, no call surfaced it), `unrecorded` (the record never held it).
