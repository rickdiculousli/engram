# Technical decisions

The machinery calls, made without the owner (they read outcomes, not machinery), each with its why. The owner's own calls are under Decisions in the private `.engram/README.md`; this doc implements them. How search and the timeline work is in [search](search.md); summaries in [summaries](summaries.md).

## How work is measured

- **Scripts first, no model usage.** A change is measured by script before anything live: whether one call's output holds each key record, and how big it is. Why: full live runs burn the week's quota, and a coverage script predicts their results.
- **Live runs are small:** about 10 questions, with a stated question each run settles, their cost reported afterwards. A full run's noise is larger than most changes.
- **What counts:**
  - a single fact: in hand after one move, the `engram now` picture plus the top 5 of the question as one search, any record code calls the same, else the key's values in one record (`evalset.fact_in_hand`, [evaluation](evaluation.md#the-bar-100)). Each row of the picture is its own record for the key's values: read as one text, it holds a key's values on unrelated rows, a hollow pass. A `now` row counts for an entry on its chain only where its own line holds the key's values.
  - a frame question: every record it needs in one timeline call, counted per record as well as per question
  - size: estimated at four characters a token, against grep's measured tokens
- **The baseline is grep** (`engram eval --mode grep`), run in a clone of the real repo with its own instructions, hooks and skills, capture off.
- **Look at the record's real items before building on it.** List every kind of file with its sections per file, decide what one real-world thing is for each, and read real output rows by eye, not only counts: a count can't see one report showing up as many rows.
- **Check a bar by arithmetic before adopting it.** At a per-record find rate of 0.89, "all records, in all 3 runs" passes a 6-record question about 11% of the time.
- **A session-origin question never sees its own session:** `ENGRAM_EXCLUDE_SOURCES` hides the session's docs from search and timelines, and its said rows (`session:<id>:…`) everywhere.
- **The sealed held-out set is never opened while tuning.** Children (subagents, `claude -p`) run at a named effort, medium or below.
- **Expected refs follow the record when it moves.** Evals match refs as exact strings (`evalset.hit`), so when a record's files move, each old ref in a set is replaced by its new homes from the move's map: array elements only, no question text, kind or note changed, checked field by field against a copy.

## Said rows

What the owner said in a session becomes rows on its threads, drawn from the stitched session summaries at ingest (`sources/said.py`), so a timeline shows what was only said beside what was filed.
- **What:** symptom reports, other reports, decisions and changes of mind, and from the chronology the entries the owner said and outside sources' words passed on, credited to that source. Claude's own analysis and advice stay out, and so do records filed during the session and open questions.
- **Placement:** an occurrence sits on its recurring thread's threads; anything else on the threads its top 10 hits vote for, keeping any within 60% of the top vote. Placing uses the ranking only (`surround=False`), so a re-index stays fast.
- **Each row** is dated the day it was said, quoted, and points to the session line: `session:<id>:<line>@said-<section>-<n>`.
- **Only indexed sessions:** a session kept out of the index (eval work) stays out.
- **Unplaced analyses:** an open question or discovery file none of whose sections is on a thread is placed by the threads its opening 80 words find as a search (`sources/place.py`, source `placed`). Only the record's own analyses are placed: placing every unplaced document found the same records for twice the tokens.
- **An entry with no thread** takes the threads of the other entries in its series, or on its thing's chain, most entries first (`events.inherited`); a pooled series gives none.

## Stable document ids

Link ends must survive a moved file or a reworded heading.
- **One registry, no front matter** (`docreg.py`, `events/docs.jsonl`): appended to only, mapping each id to its path and each anchor to its heading; the latest line wins. Why not an `id:` in front matter: anchors need a registry anyway, text files can't hold front matter, an id line would change every page the owner reads, and the pre-commit looks at moves anyway. Ids are `doc-` and six characters from the short-name alphabet; anchors four. A path row may carry `thing` (from `[nodes]`), so a renamed thing file still resolves.
- **What gets one:** every indexed document gets an id; a heading gets an anchor the first time a link points at it, since an anchor on an unlinked heading protects nothing and would make every heading edit a pre-commit question. `engram docs sync` does both in one store commit; the hourly job runs it.
- **Resolving** at read time, never rewritten: `doc-…#anchor` through the anchor's heading now; an old `path#Heading` through every path and heading the registry has held; a merged document or section through its forward. The index's link table holds where each end stands now. `engram show` takes an id or an old end.
- **New links write ids** (`engram link`, capture's placement, the re-link job), with `from_hint`/`to_hint` holding the path and heading as they read.
- **The rename check** (`engram lint --staged`): a staged change that deletes or moves a document a link points at, or drops a linked heading, is refused unless the staged registry places it. A pure `git mv` and a one-to-one heading rename are recorded by the hook itself; each refusal prints the exact `engram moved <old>[#heading] <new>[#heading]` command.
- **`events/_nodes.jsonl`** (kind, milestone, `by` and threads of record sections that aren't entries) is kept by hand; `engram nodes prune` drops rows whose file is gone, and the append-only lint lets it lose whole rows and nothing else.
- **Index excludes in the record:** `[index] exclude` in the record's `engram.toml`, merged with the domain's configured excludes; `engram exclude <path>` adds one in one store commit.

## Mechanical errors

`engram fix [<event files>] --why <the error> [--drop-link <id>]... [--drop-run <commit>]` (`fix.py`) commits the listed event files as edited or deleted, drops the listed lines from links.jsonl, and pushes: one commit, `engram fix: <why>` with an `Engram-Fix: <why>` trailer. `--drop-run` undoes an evidence sweep whole, and takes several commits when a backlog landed over several runs: it drops every link of the sweep's author those commits filed that's still there, and its message carries git revert's line for each, so the weekly page treats each run as reverted and its line goes. The pre-commit's append-only check lets exactly those paths through (`ENGRAM_FIX`). It refuses, changing nothing, when a listed file is unchanged or wasn't an event, an edit changes the id or doesn't parse, another event file or links.jsonl has uncommitted changes, a link id isn't found, a link left behind points at a deleted event, or the run named filed no sweep link that's left. The advisor asks the owner before a fix; it is for what the machinery got wrong, never for something learned later.

## Theory revisions

`engram theory change` (`theorychange.py`) takes flags for one revision, or `--ops -` for a JSON list: add-node, add-loop, insert-step / remove-step, add-join / retire-join, status. `plan()` applies the whole list to a copy of the graph and refuses on the first problem: an unknown id, a join kind or strength the record's `[links.theory]` doesn't know, a retirement without `replaced_by` and `why`, a loop left with fewer than two steps, a closed loop that no longer closes, or an open chain that's no longer one path. New steps and joins are lines of links.jsonl; a retired link gets a status entry on `link/<id>`. `theory.load(asof=...)` drops what's dated later, so `engram theory --as-of` shows what was thought then.

A structural change starts `engram theory relink --change <id>` detached (`relink.py`): every entry and document is read whole, packed into calls of at most 90k characters, and code keeps a new link only if its record is in the batch, its target is part of the change, its rel is strengthens or weakens, and it isn't held already. Links are by=claude. A change runs once; the hourly job runs one still queued after 10 minutes or left running for 3 hours; one that errored waits for a hand rerun, since a retry spends money, and shows one line in `engram now` until it's rerun.

## The evidence sweep

`engram theory sweep` (`relink.sweep`, beside the re-check) links the whole record's evidence to the theory's loops and Discoveries, which the re-check never does on its own: it reads only after a structural change, and the filer writes timeline links and agreed joins, never evidence.
- **What it reads:** the re-check's records (`records()`, the pack's `relink_skip` left out) without journal entries, in calls of at most 30k characters at medium effort, each with every loop (its path drawn) and every Discovery whole, in the pack's `sweep` words. Why: in the re-check's 90k batches at low effort, a call holding hundreds of short entries missed most of what bore on the theory. Questions are phrased either/or, so for and against mean nothing for them, and nodes, states and treatments are left out because the theory block never prints their evidence.
- **The guards are the re-check's** (`_check`): the record is in the batch, the target is a loop or Discovery, the rel is strengthens or weakens, and the pair isn't linked already, by any evidence rel and in any form a target is named (its id, its file, a section, its document id). The read also cites the record's own words that bear on it (`passage`), found word for word in the record. A document's passage that restates one entry is that entry's evidence: one entry's own words (a table line), or a dated index row (a date, a dash, a headline) whose row links to the entry or whose headline is the one entry's title, that day's when several are. The link moves to the entry (`_entry_of`), and "already linked" drops it as a repeat; a passage no one entry fits stays the document's. Why: pages restate their entries' headlines, and one observation was counted under the same target several times. The re-check applies the same guard.
- **A second call confirms each link** (the pack's `sweep_confirm`): it sees the record whole, its passage, the target and the rel, never the read's reasoning, and only a yes is filed. Why: a weekly machine read with no owner in the loop needs an independent check before anything lands; shown the record alone, it turned down links whose evidence was one passage of a long document. Asking it twice adds nothing: the same prompt gets the same verdict.
- **Filing is the re-check's transaction** (`_file`): by=claude, author `engram-sweep`, the passage as the link's note, Claude's placement, never the owner's claim, in one commit whose `Refinement:` line is the weekly page's. `--dry-run` files nothing; `--out` writes every proposed, dropped, confirmed and rejected link.
- **A run never starts a call that could take it past $10** (`SWEEP_CAP`: it leaves room for its dearest call so far), and the next run picks up where it stopped. Its progress (`sweep/<domain>.json` in the data folder; a dry run keeps its own, `.dry.json`) holds each record read and at which text, and the links still to confirm or file: a run confirms what waits first, then reads only records new or changed since, and all of them again when a loop or Discovery is added or goes. Why: a record's whole backlog can cost more than one run may spend.
- **Links engram placed stay open to the theory work** (`recheck`): only `engram-sweep`'s and `engram-relink`'s, by=claude, never the owner's. They're read again by the confirming call, in the same words, against the target as it stands now: when a structural change revises their loop (`run`, before it reads), when a weekly run finds their loop or Discovery's text changed since its last read (the progress keeps each target's version, the hash of what the calls see of it), and on request, `engram theory recheck <target>`. A no drops the link through `engram fix` (`--drop-link`), one commit per run whose `Refinement:` line is the weekly page's, and remembers it against that version of its target (`sweep/<domain>.dropped.json`); a guard of both the sweep and the re-check refuses it until the target changes. Re-reading against an unchanged target gives the same answer, so a sharpened claim is what prunes a stretch.
- **Weekly:** `engram refine run` runs it for each domain whose pack has `sweep` words, before the passes, once a week by its own mark. Its ledger rows (`job: sweep`) count toward the week's spend, so the passes' money left counts them, but the passes' "already ran" check and status ignore them; `engram health` tells its outcome, a $10 stop or a failure included (an unknown cost counts its whole cap). It's skipped when the repo is paused, and a dry run runs nothing.
- **A replay** (`--replay FILE`) lands an approved set with no model calls: the recorded proposals answer each read and the approved (passage, target, rel) answer the confirming call, and every guard runs against the record as it stands. Why: a set read against a scratch copy lands on the live record exactly as approved.
- **Undo** is `engram fix --drop-run <commit>` ([mechanical errors](#mechanical-errors)).
- **Left out:** corrections and disagreements (a machine read can't tell a correction from separate occurrences by the record's own fields; that belongs to the filer, at filing time).

## The filer

The hourly job (`engram capture run`: `hourly.py` runs it and the session start's health check, `capture.py` files, `setup.py` installs and repairs) indexes changed sessions, keeps the set-up repos' summaries current, files each session that grew and has been idle an hour, summarizes the long records of each area it files for ([summaries](summaries.md#record-summaries)), and repairs the install.
- **Routing:** a session belongs to the repo it was started in (its project folder name, else its first working folder), a subfolder or a worktree of it.
- **It reads the session whole,** cleaned like the summaries, from the message it last filed up to. A session still going is skipped. Most sessions file nothing, and are still marked. The model sees what the session already filed, read from the store by `source` (`said in session <short id> ` or `agreed in session <short id> `, without its placement links and renewals), so a refiled session doesn't file it twice; the mark is the only state kept per session. Why: the record is the one copy of what was filed.
- **Code drops a fact** unless it's from the owner's own words: its quote in one of their messages past that point, word for word, and every number in their words or the question they answered. That question must be in Claude's turn just before their message (`capture.turn_before`): all Claude's text since their previous message, past a skill's turn, a summary or another speaker, and the current turn's text before what they sent while Claude worked. A number counts only whole (`dates.numbers`): "35" isn't in "135B", while "7 out of 10" passes on "7/10".
- **What the model sees of the record:** every entry dated within 31 days either side of each message's day, where each tracked thing stands (the `now` chains), and search hits; any fact a listed entry states, in any words, is a repeat.
- **The repeat check:** after the code checks, each candidate's own title and body search the index; its top 8 hits across entries, documents, occurrence pages and where-things-stand, whole up to 1,500 characters, plus every entry dated the same day, go to one low-effort call per session (`verify`), which names the record that already states each repeat. Code drops it only if that ref was shown under it. A new occurrence of a known thing is always filed: for an occurrence kind (the pack's `occurrence_kinds`), the named record's date must fall within 2 days of the candidate's (4 when either is approximate). Why: searching by the owner's raw words missed records worded differently.
- **Dates never said:** code checks the model's date against the message and the question answered (`capture.said_date`): the day said, a day relative words count back to, a weekday or weekend named, a date written out, a month or year by name. A day that fails narrows to the month or year that passes, else `date: not-sure`.
- **Kinds from the pack:** the filer offers the entry kinds its pack names (`kinds`), and files anything else as the first; a pack that names none offers the kinds the record already holds, most used first, with anything else an observation. Why: an area whose filer must write only one kind (a compiled area's sparks) can't be steered by what the record happens to hold; the fallback keeps a pinned pack's prompts as they are until its own pass names its kinds.
- **Placement when filed:** the same call returns each fact's threads, `occurrence_of` and `led_from`; code keeps only known threads, an existing occurrence page and an entry the record holds, with rels its `[links.timeline]` allows. No extra call.
- **Theory changes:** the job files a status change or a theory link only when the owner states it or agrees to Claude's proposal; code drops an unknown id, status, rel or strength, a repeat, and anything not in the owner's words. When the owner agreed to a structural change, a second call writes the operations, and `plan()` checks them before `apply()`.
- **A thing's chain:** a change joins the chain its name matches (`now.chain_for`), strictest first: as written, strengths dropped, forms dropped, a prefix, then a name of two words or more inside a longer one.
- **Failures:** a reply with no JSON raises, so the session's mark stays; a summaries run that stops (the model unavailable) or a record summaries run that fails is the hourly run's error; a failed commit takes back what its transaction wrote; a failed push, or one that hangs past its timeout, is a row in `capture.sqlite`'s `push` table, shown at session start and retried hourly. `engram capture status` counts each session's entries from the store, and lists uncommitted entries, unpushed commits and a failing push; `engram capture refile <prefix>...` clears marks so the next run rereads a session.
- **Renewals,** a step after the filer and apart from it (`capture.renew`): a thing marked "last mentioned" ([shape](shape.md#identity)) clears when the owner says they're still on it. Code runs it only for a session where the owner, or Claude's message they answer, names a thing marked that day, generously (every form of its names, and each word of four letters or more); a session naming none makes no call. One low-effort call sees those exchanges (Claude's message cut to its end, where a question sits) and the marked things, in the pack's `renew` words, and answers per thing with the owner's quote or nothing. Code keeps one only for a thing marked that day, on an exchange that names it, with the quote word for word in the owner's message and any question answered in Claude's turn just before (`_his`); one a thing a session. It's filed as a `renewal` entry on the chain, which only the mark's date reads, and the filer's list of kinds leaves it out. A failed renewal is logged and leaves the mark. Why apart: teaching the filer to keep "still on it" changed what else it filed, twice.
- **The session start fits whole:** Claude Code shows a SessionStart hook's output whole only up to 10,000 characters, a fixed limit; past it Claude gets a 2 KB preview and a file. The hook keeps to `hourly.HOOK_BUDGET` (9,000): its other lines are printed whole, and the picture gets what they leave, cut from its end at a line, with a pointer to `engram now`, which prints it uncut. So the picture puts first what a session needs first: upcoming, the theories and open questions, then where each followed thing stands and the team, and last the things stopped over a month ago, which a cut takes first. Why the cut: a long record's picture sits near the limit, and the margin is small.

## Setup

`engram setup <repo>`, for a repo whose rewiring is current, installs, idempotently, the session-start check (`engram capture check`), `Bash(engram:*)` in the allow list, a Bash window that fits engram's output (unless the repo sets one), the git pre-commit ([data model](data-model.md#the-pre-commit)) and the hourly job; `engram teardown <repo>` removes exactly those, restoring the settings file byte for byte; `engram capture status` (also in `engram health`) shows them, each session's last filing, the last repair and the job's last run. Every hourly run and session start repairs a missing or stale piece.
- **Teardown takes the run's lock** (`hourly.lock`), waiting if a run holds it, so a run started before can't commit into the repo after.
- **A launcher counts as current** when it imports this code (`setup.code_of()`), not when its path matches.
- **Claude's Bash window:** setup writes `bashOutputMaxChars` (`setup.BASH_BUDGET`, 100,000) into the repo's `.claude/settings.json` when the repo sets none, and only where it's set does the session start tell Claude to read engram's output whole, one engram command per Bash call. Why: Claude Code shows a Bash output whole only up to that window (30,000 characters unless set, 4,000 to 128,000), and a long record's timeline is past the default, so Claude cut it or got a preview. The window holds for every Bash command in the repo, not only engram's, and costs tokens only when an output is that large; a project's value beats the owner's own global one there. A value the repo already has is kept at any size, and teardown drops only one setup added. Claude Code can override the setting remotely, per tool, with no sign, so a release checks that a long output still arrives whole ([operations](operations.md#the-release)).

## The instance lives in config

- **The code names no instance.** Whose record it is (`owner`), the domains, the archive's mirror, the second box the daily copy goes to (`[daily]`) and the folders of sessions rewiring reads (`[sessions] roots`, a mirror among them; Claude Code's own by default) come from the box's `~/.config/engram/config.toml`. A domain (`[domains.<name>]`) sets `repo`, `remotes`, `exclude`, `sessions_from` and `pack`; every one the config declares is served, in its order, and `general` is built in.
- **`ENGRAM_CONFIG` names a file laid over the box's config,** table by table: a scratch copy or the frozen gate points a domain at its own clone and keeps the owner and the excludes.
- **Prompts name the owner from config.** A template writes `{owner}` and `{owner_id}` (the name in lower case, a record's `by`), and `config.voice` fills them.
- **The guardrails are engram's own hooks** (`.githooks/`). The pre-push refuses to send a public remote anything built on the private history, which only the remote named `archived` keeps. The pre-commit checks: no tracked `.venv`; the public tree (code, tests, docs, bench, skills, examples, README) names no instance on any line (the owner, their home folder, each configured repo's path and remotes), and `src/` no configured domain's name either; the tests pass; each pack the box pins passes its own tests at its pin; and under the weekly pass, nothing staged in what it may not change (below).

## Packs

An area's words and a few small functions live in its own record repo, under `.engram/`; core does the work ([shape](shape.md#a-pack)). Everything engram keeps in a record repo is in that one folder: the pack, the record's `engram.toml`, its git hooks, the weekly pass's specs (`specs/`), and one page, `README.md`: the owner's jobs, the area's decisions, its design when it has one, and how the weekly pass may change the repo, in that order. The pack runs from a pinned commit; `engram.toml` is read from the working tree (`paths.record_toml`), since `engram exclude` writes it.

- **What a pack holds** (`engram.pack.Pack`): `prompts`, the words of each model call engram makes for the area (`file`, `verify`, `record`, `renew`, `theory`, `structure`, `relink`, `relink_system`, `sweep`, `sweep_confirm`, `recsum_system`, `compile`, `compile_post`, `compile_spark`, `health`); `kinds`, the entry kinds the filer may write; `current`, what "where things stand" follows (an entity kind and its statuses, detail field and name forms, thread prefixes and their sections, upcoming, the people seen); `occurrence_kinds`, where a repeat must be the same occurrence; `relink_skip`, the paths the evidence re-check never reads; `read`, a reader per source for what core can't read, and `on_request`, the sources too big to read before each search; `summary_rules`, what the session summarizer adds for the area, under its own version; `health`, a line on what's wrong between the repo and the pack. The theory graph, its revision and re-check, current, said, placement and the timeline stay in core as features any area gets.
- **A reader** gives the index's own records (`Doc`), the links among them (`revises`, `disagrees`; their family is the source's name) and the ways in they open. Core fills `{owner_id}` in an author and a date's sort key, cuts a long record into chunks, indexes each source under its name and rebuilds the ways in with the reader's. A source read on request gives records only: `engram ingest --source <name>`, or `all`. A file under a folder named in the record's `[index] spines` sits on the spine its subfolder names.
- **What isn't in a pack:** an area with no `file` words is searched, never filed for: `engram setup` refuses, and `file_session` raises. With no `current`, `engram now` shows only what the theory graph and the people list give. Recurring-thread pages come from the record's `[ways.symptom] pages`.
- **The pin's tree** (`pack.tree`) is the id of `.engram/` without the page, `specs/`, `engram.toml` and `hooks/`: those change while the pack doesn't, and the gate and a release compare only what runs.
- **Loading.** `[domains.<name>] pack` is a commit of the record repo or an absolute directory (a worktree, a scratch clone, a test). A commit is extracted once with `git archive` into `~/.local/share/engram/packs/<name>/<commit>/`, read-only, through a temporary folder renamed into place, so parallel readers never see half a pack. It's imported as `engram_pack_<name>`. Nothing in the record's working tree runs: a commit there is inert until it's gated and pinned.
- **The owner's words leave out every session an agent started** (`sessions.by_agent`), for rewiring's turns, check's any-session quotes and the weekly pass alike: a headless run, or a first message that opens as T3's delegates and other agents do; a brief is judged message by message (the weekly pass, rewiring's turns), and the filer and summaries use the same session rule. A delegate's report and an agent's hand-back are never turns. T3's delegate puts "Act as the <role> sub-agent for this task." before every brief, and nothing structural tells such a session from the owner's own T3 sessions (same entrypoint, worktree and permission mode), so the opener is the mark.
- **Drift is judged on what's committed.** `[rewire] at` is the id of the jobs and failures a rewiring answered (each item's bold name and its quotes), not a commit: a commit can't name itself, so the commit that changes the jobs moves `at` with them. Prose around the items, or elsewhere on the page, isn't drift. `engram rewire check --drift` reads the index (inside a hook, the one git names), HEAD and, in a conflicted merge, MERGE_HEAD, and refuses only the signs the index has and neither of those does, so the pre-commit judges the commit being made: drift that reached HEAD another way (a pull, a `--no-verify` commit, a release whose copy detection finds more) is `engram health`'s to show, and never stops a commit, the filer's included. It skips the history scan, so it runs on every commit unnoticed.
- **Isolation.** A pack may import only the standard library, pyyaml and `engram.pack`, checked before it's imported. One that fails to load is its domain's alone: nothing is filed for it and its `current` rows stay as last indexed; `engram health` and the session-start hook say why. `.engram/` is in every domain's index excludes, and the loader reads only its Python files.
- **Tests.** An area's behaviour is tested in its pack's `tests/`, which run with engram: `uv run pytest <repo>/.engram/tests`. Core's tests file through `examples/notes/`, a small made-up area whose pack sets only words.
- **Left in core:** the canon's vocabulary that the summaries' format and the index already speak (story, complaint and series prefixes, clinician labels, the summarizer's base prompt and its examples, whose move would change the prompt's bytes and so needs a versioned summary QA), and waysin's treatment builders and its pooled-series name.

## The compiled wiki

`intake.py`, `compile.py`, `wiki.py`, for the owner's calls that knowledge needing ingesting is compiled and that its wiki is a traditional one, of concept articles ([data model](data-model.md#sources-sparks-and-the-wiki)).

- **Intake** fetches a page with the standard library and reads it to text by `html.parser`, keeping the URL; a video or an image arrives as the advisor's reading, marked `transcribed_by`, with the file kept by its sha256 under `events/files/`, which the append-only check already guards. Why sources are entries and not a new store: entries already carry title, author and date, so a hit mid-article shows who said it.
- **One page model** (`wiki.Concept`, `wiki.Source`): a page's properties and sections as typed data, rendered to Obsidian markdown and parsed back byte for byte; the checker, the splicer, the index and the health check all read it. Why: the model's edits are data that code applies, so everything outside an edit stays as it was, and that's checked rather than hoped for from a model rewriting a page.
- **Compile:** one Opus-low call per item, in the pack's words (`compile` for a source, `compile_post`, `compile_spark`), given the item and every concept's first sentence and numbered steelmans. A source's reply names at most five concepts it bears on, each with the source's words, its position, steelmans and answers, plus the source's summary and key quotes; a post's sets its line under "In your writing" and may revise a summary, answer a steelman or bring a new concept; a spark's names the one concept it bears on, and code writes the spark verbatim there and on the source that set it off. Code splices the edits into the pages as HEAD holds them: an old entry is never rewritten, a summary changes only on a post or a spark (or a new concept), and a `[[Name]]` the model writes becomes that concept's link, or its plain words when no such concept is there. Why one call per item for all its concepts: the item's text is sent once.
- **The checker** (`wiki.check_concept`, `check_source`, `kept`): properties and sections as the model says; every quote word for word (`verbatim.found`) in what it cites, a spark's in a spark, a source's summary sentences as recsum checks one; every link resolving as Obsidian resolves it, against `.md` files, or to a page made in the same compile; a steelman from a source quoting it, one of Claude's own quoting nothing; an answer quoting what it links, else it counts as unanswered; a source's position one short sentence after its words; everything outside the edits byte-identical. A failing page is asked for once more with its problems, then parked as (item, concept) in `open.md` while the pages that pass land, links to it taken out of them. A source page that fails fails the item.
- **Commits:** one per compiled item through `Store.transaction`, its pages as the paths, and the compiler writes only under `wiki/`. Its commits carry `ENGRAM_WIKI`; the pre-commit refuses any other change under `wiki/`, naming the paths and the one command that puts them back, and refuses `[[` or `> [!` added to the folders `[wiki] plain` names. Why commit the wiki: it's written work, costly to write again, and git keeps its history.
- **What was compiled** is the data folder's (`compile/<domain>.json`, by item and text hash, with the parked pages and the health check's findings): a source or spark is compiled at once and once, a draft once its text has stood a day unchanged in git (a pure rename isn't a change), a post at once when it's published, and an item whose call fails twice at the same text is parked until it changes. One run per area at a time (`compile/<domain>.lock`). The hourly job compiles what's due; `engram source add` compiles its item before it returns.
- **A moved post:** a post gets its stable id at its first compile, the pre-commit records any move git sees of a document with an id, and each run first points the wiki's links to a moved post where the registry says it went, by code.
- **The index and the open list** are written by code from the pages at the end of each run and health check, committed when they change; a rebuild is byte-identical. The index lists the concepts by pillar, each with its summary's first sentence, its sources, its steelmans and how many are unanswered, and, while no post uses it, its sparks (a post to write); then the sparks no concept has taken and the latest sources. The open list holds what couldn't be compiled or hasn't been, the parked pages, links that go nowhere, answers that no longer check, concepts nothing links to, and the health check's findings.
- **The health check** (`engram wiki check`, and after each repo's weekly pass, its cost the pass's): one call over every concept's summary and the sparks no concept has taken. Merges are applied by code: the kept page takes the other's name as an alias, everything the other held is appended, and every link is repointed. Splits, contradictions, a concept for three or more sparks that share a thread, and gaps wait in `open.md`; nothing is fetched until the owner says go. Why only merges are applied: a merge loses nothing and its alias keeps the old name working, while a split needs new prose.
- **Quote matching** (`verbatim.norm`) treats every dash as one hyphen, an ellipsis as three dots, and a word hyphenated across a line as one word. Why: page text and transcripts break words and dashes where the model's copy doesn't.
- **A thin repo's jobs:** `engram rewire turns --session <id>` adds the owner's turns from a jobs interview held elsewhere, so a repo the owner hands things to more than talks in can cite them.

## Building without touching what runs

- **The hourly job runs from a release checkout at a tag** ([operations](operations.md#the-release)). The tag moves forward only when the frozen gate passes; rollback is moving the tag back. Builders work in worktrees. Why: an editable install made any merge live within the hour, in a job that commits and pushes a record.
- **Only the release repairs the box's install** (`setup.refused`, shared by setup, every repair and the daily and weekly jobs' installs). Once the box's own data folder has a loaded install, an engram running from anywhere but the release clone (when there is one) sets up and repairs nothing and installs no job; under another `ENGRAM_DATA` no job is written or loaded, and a repo the real install serves keeps its settings and hooks. A piece left alone isn't a repair, so it records none. Why: a worktree's `engram capture check` called the release's hooks old and repointed the real repos and job at itself, and a scratch copy holding the real rows rewrote them with its own data folder.
- **Index changes are additive.** New columns are nullable, added by `ALTER TABLE` in one change, after the `.sqlite` files are copied; once every index and usage log has one, it moves into the schema and the upgrade step goes. A rebuild from source would drop sessions older than Claude Code keeps, which survive only in the index and the session mirror, so the rebuild drill uses the mirror.
- **Commit messages engram writes come from fixed templates** (`commitmsg.TEMPLATES`). In the hourly path an amount the figure check finds (`figures`: a whole number read with its money, magnitude, percent or share marks) is stripped, not refused: a refusal rolls back the filing transaction, and it would fail again every hour.

## Scratch copies

- A scratch copy is evaluated with `ENGRAM_DATA=<copy>/data ENGRAM_CONFIG=<copy>/config.toml`.
- **A scratch index stays frozen:** searches skip the automatic refresh when `ENGRAM_FROZEN` is set or the data folder is under `scratch/`. Why: a live check's searches pulled a new session into a scratch index and moved a result.
- The real record is untouched until the before-and-after review, and changes land as reviewable per-file commits.
- **`ENGRAM_SANDBOX=1`** keeps commits local, skips pushing, and writes index and usage rows to a temporary directory. Eval runs set it.

## The weekly refinement

`refine.py`, for the owner's call that a weekly pass refines engram and each repo it serves.

- **Which repos:** engram's own (`[refine] repo` in the config), then every configured domain's that has its page (`.engram/README.md`); one with `[refine] paused = true` in its `engram.toml` is skipped. No separate list: a repo engram owns is one the pass serves. Why the page: it's what the pass answers to, and a folder configured only for search has none, so it gets no specs.
- **The pass** is `claude -p` handed `skills/engram-refine/SKILL.md` by its path in engram's own repo, so an edit there steers the next pass without a release. It runs in the data folder's `scratch/refine/`, outside every repo, so no repo's session-start hook or filer sees it.
- **The pass runs engram fenced** (`refine.fenced`, in the pass's env): `ENGRAM_DATA` is a copy of the data folder (each SQLite file, the value review's too, through SQLite's backup, and the moved refs) in `scratch/refine-data/<week>-<repo>/`, cleared at the next pass's start, with capture's repo rows dropped so nothing run there serves a real repo; `ENGRAM_GATE` is the real gate folder, for the baseline; `ENGRAM_CONFIG` lays a `repo` over the box's config for the domain under pass only and `repo = ""` for every other (all of them on engram's own pass), the shape the gate's freeze writes. engram's `.githooks/packs.py` and `instance.py` drop `ENGRAM_CONFIG` and read the box's own config, so the pass's commits in engram are checked as anyone's. The fence covers what finds a repo through the config: `theory change`, `recheck` and `sweep` by `--domain`, and the wiki's domain lookup. `add`, `link`, `exclude`, `source add`, `nodes prune`, `fix`, `wiki`, `moved` and `docs` take `--repo` or the cwd, and Bash and git are outside it: it guards against accidents, and adds no more machinery. Under it engram's own pass can't `show`, `now` or `theory` another repo's records; its evidence is the conversations and the value review's findings. Why: a pass is given one repo, and the data folder and the other repos are the owner's live record.
- **What the pass may not change in engram's own repo** (`refine.OFF_LIMITS`): `bench/gate.py`, `skills/engram-refine/` and `.githooks/`. The pass's env carries `ENGRAM_REFINE`, under which engram's pre-commit refuses a staged change to any of them (`claude -p` passes its env to the `git commit` it runs, and the refusing hook is the worktree's own copy, hence `.githooks/` on the list), and its settings deny `Edit` and `Write` on them. It guards against accidents: `--no-verify` and the fast-forward merge skip the hook, and a Bash write passes the deny rules (the hook still catches its commit). An approved spec that names one of them is built in a session; the pass leaves it `approved` with `blocked:` saying so, as an outcome. Why: the gate measures the pass, the skill steers it, and the hooks check it, so a pass changing them would grade itself.
- **What it tells the owner** travels with the change: every landed commit carries a `Refinement:` trailer, its line, and one the owner wouldn't see opens it with `none:`, which keeps it off their page; `.engram/specs/` holds what waits on them, and an approved spec a pass couldn't build says why in `blocked:`. After a run's passes, unless none ran or a dry run, `digest` reads both from git and the working tree of every repo the pass serves; when anything waits (an open spec, an approved one with `blocked:`, a change they'd see not yet on a page, jobs still proposed), one `claude -p` with no tools turns them into the week's one self-contained HTML page, `refine/digests/<week>.html` in the data folder, each item under its repo, which opens in the browser, and only then are its changes marked shown in `refine/seen.json`. When nothing waits, nothing is written or opened. The run's report names the page, and a run later in a week that has its page leaves its items for the next. So a revert takes the line with it, no file of notes can drift from what landed, and a page that fails leaves its items for the next. It runs in the run's own process, which no session holds, and its cost (up to `DIGEST_CAP`) is its own ledger row (`job: page`), within the week's cap. Why one page a week, and only when something needs the owner: it's for reading, not acting, and the owner answers each item in a session in its repo, which reads the specs from disk; never at session start.
- **A deferred spec** (`status: deferred`) is on no page, and no pass builds or re-specs it, until the owner raises it again. Why: the owner put it off; showing it each week would ask again.
- **Session start** (`engram refine surface`, from a set-up repo's `engram capture check` or a read-only repo's own hook) shows only, for the agent, a spec or page here or in engram's own repo whose front matter won't parse. Why: a session's edit is how one breaks, and a broken one drops off the page unseen.
- **Spend:** each pass's cost goes to `refine/ledger.jsonl` by week (from Saturday, so the Sunday and Monday catch-ups count in it); an unreadable result counts as the pass's whole cap, as does a pass that times out at `[refine] hours`; one that never starts costs nothing.
- **A pass's cost is written before it starts,** at its cap, and replaced when it ends: a pass stopped mid-run keeps its cap spent, so nothing reruns it for free. A pass that failed at a cost is the week's; one that failed for under $1 (as when it never started) is retried at the catch-ups. A pass on request (`engram refine run --repo`) first checks the repo isn't paused, the week's cap isn't spent and no pass is running, says why if one is, and then starts on its own, kept awake, so no session's time limit cuts it off. The schedule waits out a pass that holds the lock rather than giving up its firing. Why: a pass may run for hours, and a session stops its background commands within two. A failure is told in `engram health`, never at session start: the owner reads outcomes. Why: a pass that fails the same way each time would otherwise spend the week's budget again and again.

## The value review

`review.py`, for the owner's call that every repo on engram can call a review of engram's value (in the private `.engram/README.md`).

- **When:** in the hourly job, for a session idle an hour, at most one a day per repo, in a repo whose `engram.toml` sets `[review] on = true`; on demand, `engram review <session>`. Off by default.
- **What it reads:** one Opus call at high effort with no tools. For each of the owner's asks: their words, each engram call the advisor made with what it returned, the answer, and engram's own first call on their words as of the session's day.
- **What it returns:** findings as JSON, each with its question (`data`, `path`, `balance`), the ref, the call that should have surfaced it, what was missed, and its cause: `advisor` (a call returned it), `tools` (the record held it, no call surfaced it), `unrecorded` (the record never held it).
- **Where they go:** every finding is recorded with its cause, and the call it names written out, in `review/review.sqlite`, beside each review's cost. The weekly pass on engram's own repo reads the week's `tools` findings after its conversations (`engram refine conversations`). The review itself lands no code and tells the owner nothing at session start. Why: the owner's call makes it evidence for the weekly pass, which is where engram's tools change.
- **Never captured:** its prompts open with `engram value review`, and a session that does is never reviewed.
- **What it sees:** only engram's own calls. On a session where the advisor read the record files directly, it judges the answer against what the record held.
